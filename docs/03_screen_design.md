# 旅行アルバム 画面設計

## この文書の位置づけ

旅行アルバムの Flutter アプリ（`mobile/lib/`）の画面を、利用者から見える振る舞い（画面の要素・文言・遷移・ダイアログ・エラーの出方）で書く。
**この文書は未実装を含む目指す姿**で、実装した画面には「実装済み」の印を付ける（2026-10-25 に、旅行アルバムの設計一式（以前の `docs/travel-album/`）をこの `docs/` に移し、植物図鑑の頃の文書を置き換えた。人間が決定）。
設定画面（§4.9）とアプリの作りの方針（§9）は、以前の植物図鑑の画面設計・技術選定から移した。

段階2の画面は実装できる粒度で、段階3・4の画面は骨格で書く。各画面の見出しに段階を付ける。
API の形は [05_api_design.md](./05_api_design.md)、送信や保存のデータの形は [04_data_design.md](./04_data_design.md) を参照する。
文言はこの文書で決めたもので、第3版（設計案）には無い。変えるなら実装前に決める。

### 状態の持ち方（段階2）

CLAUDE.md「実装の慣習」の Flutter の構成方針（`setState`、コンストラクタ注入、`Navigator.push`）を守る。
画面をまたいで共有するのは次の2つだけで、どちらも `AppRoot`（`lib/app_root.dart`）が1つ作って各画面のコンストラクタに渡す。

| 共有するもの | 型 | 理由 |
|---|---|---|
| `ApiService` | 既存 | 2タブが同じ設定で通信するので、根で1つ作る（以前は `PlantListScreen` が自分で作っていた） |
| `UploadQueue` | `ChangeNotifier` | 送信は画面を移っても続く（要件 5.2）。画面の `State` に置くと画面を閉じたときに消える |

`UploadQueue` の購読は `ListenableBuilder` で行い、状態管理パッケージは入れない。
「画面をまたいで共有するクライアント状態」（お気に入りなど）はまだ無いので、CLAUDE.md の「見直す条件」には当たらない。

設定（API キー・エンドポイント）の読み込みと「API設定が完了していません」の扱いは `AppRoot` に移す。
植物一覧画面が持っていた起動時の挙動（API キー未設定なら設定画面を自動で開く、設定画面から戻ると設定を読み直す）は、
`AppRoot` が2タブの外側で同じように行う。各タブの画面は `ApiService` を受け取って一覧を出すだけになる（植物一覧画面は 4-5 で図鑑画面に差し替えた。§6.4）。
エンドポイントにも既定値は無い（本番の URL をアプリに組み込まない）。API キーかエンドポイントのどちらかが無ければ、タブを出さずに設定を促す表示にし、起動時は設定画面を自動で開く。

## 3. 全画面共通

- 画面左上の戻るボタンと端末の戻る操作は同じ動きをする（選択モードなど、画面ごとに書いた例外を除く）
- 端末の文字サイズ設定は反映しない（倍率 1.0 に固定。§9.1）
- アプリは端末の言語によらず日本語で動く（Material の部品の文言も日本語。戻るボタンの説明は「戻る」。端末では漢字・かなを日本語の字形で出す。Web 版の字形はブラウザの言語による。§9.1。実装済み。日本語の設定の作業単位）

- 処理の結果はスナックバーで知らせる。API の失敗の文言は `ApiException.userMessage`（ステータスで決まる固定文言か、サーバの `error.message`）。
  `ApiException` 以外の失敗では画面ごとの固定文言（各画面の表に書く）
- 一覧の読み込みは「読み込み中...」「0件」「取得に失敗」の3状態を持ち、失敗時は「エラーが発生しました」・文言・「再試行」ボタン。
  下に引っ張ると読み込み直す
- **写真の一覧はページで読む。** `GET /api/photos`（と段階4の `GET /api/catalog/entry`）は1回に 100 枚（サーバの既定）を返し、`continuationToken` が `null` でなければ続きがある。
  グリッドの下端に近づいたら次のページを読み、末尾に「読み込み中...」を出す。次のページの取得に失敗したら末尾に「続きを読み込めませんでした」と「再試行」。
  下に引っ張ると先頭から読み直す（トークンは捨てる）。規模が大きくなっても1回に読む量は変わらない（[04 §5.3](./04_data_design.md#53-旅行の写真一覧)）。
  続きを読んでいる間に読み直した場合、遅れて届いた古い続きは捨て、続きは読み直した1ページ目のトークンから読む。
  ページが空でもトークンがあれば続きを読む（サーバは空のページを読み直しても空なら、トークン付きで返すことがある）。
  引っ張って読み直すのは写真の一覧だけで（図鑑の項目詳細は、見出しが写真のページと同じ応答に入っているので見出しも読み直す。§6.2）、旅行詳細の見出し（枚数・期間）と旅行に属さない写真の画面の枚数は取り直さない（画面を開き直すと取り直す。複数選択の操作の後と、写真ビューアから戻った後と、その画面宛ての写真の送信が一区切りついた後も取り直す。§4.4・§4.5・§4.6・§4.7）
- **撮影日時はタイムゾーン無しの文字列**（`2026-10-05T12:30:15`）で、端末のタイムゾーンに変換せず「2026年10月5日 12:30」と表示する。
  グリッドの各サムネイルの読み上げのラベルも撮影日時（撮影日時が無ければ「撮影日時なし」）
  （撮影した土地での時刻として扱う。要件 5.2）。`DateTime.parse()` の結果に `toLocal()` を掛けない（Z が無いのでローカル扱いになるが、
  表示のためだけに使い、変換はしない）。撮影日時が無い写真は「撮影日時なし」
- サーバが付ける日時（`createdAt`・`uploadedAt` など。UTC の ISO）は、既存の植物詳細と同じく端末のタイムゾーンに直して表示する
- 旅行の期間は「2026/10/05 〜 2026/10/08」。同じ日なら「2026/10/05」。撮影日時のある写真が無ければ「撮影日時なし」
- 画像は `cached_network_image` で表示する。キャッシュのキーは URL ではなく `photo-<id>`（原寸）/ `thumb-<id>`（サムネイル）。
  **SAS 付き URL は応答のたびに変わるので、URL をキーにするとキャッシュが効かない。** 写真用に上限を上げた `CacheManager` を使う
  （`utils/photo_cache_manager.dart`。既定の 200 件では数百枚の旅行で入れ替わり続ける）。旅行一覧の表紙は応答に写真の id が無いので、
  SAS（クエリ）を除いた Blob の URL から `cover-<ホスト><パス>` をキーにする
- SAS の期限（`urlExpiresAt`）が過ぎた URL は 403 になる。画像を読み込めないサムネイルには「画像を読み込めません」と出し、自動では取り直さない
  （画像そのものが壊れていると取り直しが止まらなくなるため）。下に引っ張れば一覧ごと新しい URL で取り直せる
- サムネイルの読み込み中は灰色の枠だけを出す（3列のグリッドで1枚ずつ文字を出すと読みにくいため）
- 写真の一覧を下に引っ張って読み直す間は今のグリッドを出したままにし、失敗したらエラーの文言をスナックバーで知らせる（グリッドは残す）
- 旅行詳細では、写真の一覧が 404 `TRIP_NOT_FOUND` を返したら（先頭・続き・読み直しのどれでも）、上の失敗の表示ではなく画面全体を「この旅行は削除されています」にする（§4.4）
- **自動の再試行はしない**（既存と同じ）。例外は送信キューで、通信の一時的な失敗（ステータス 0 / 429 / 503）に限って 3 回まで送り直す（§4.7）

## 4. 各画面の詳細設計（段階2）

### 4.1 ホーム（下のタブ）

```
┌─────────────────────────────────────────┐
│ （選んだタブの画面）                    │
│                                         │
│                                         │
├─────────────────────────────────────────┤
│      [図鑑]              [旅行]         │ ← 下のタブ
└─────────────────────────────────────────┘
```

- 下のタブは「図鑑」「旅行」の2つ。起動時は「図鑑」で、起動するとすぐ図鑑（§6.1）が種類の一覧（`GET /api/catalog/kinds`）と最初の種類の項目を読む。
  「図鑑」は 4-5 から新しい図鑑の画面（それまでは植物一覧画面。4-3a から 4-5 までは新しい図鑑を3つ目のタブ「図鑑（新）」に置いていた。§6.4）
- タブを切り替えても各タブの画面の状態（スクロール位置、読み込んだ一覧）は保たれる（`IndexedStack`。旅行のタブから図鑑に戻っても図鑑は読み直さない。[02 §5](./02_design_overview.md#5-人間に決めてもらう点推奨付き) #36）
- 設定ボタンはどのタブの画面上部にもあり、同じ設定画面を開く
- 設定画面から戻ったとき、エンドポイントと API キーが変わっていなければ、開いていたタブと各タブの状態をそのまま保つ。変わっていればすべてのタブを作り直し、新しい設定で読み直す（開くタブも起動時と同じ「図鑑」に戻り、図鑑は新しい設定で種類の一覧から読み直す）
- API キーかエンドポイントのどちらかが未保存のときは、下のタブを出さずに「API設定が完了していません」「設定画面で API キーとエンドポイントを入力してください」と「設定を開く」ボタンだけを出す（文言はどちらが無い場合も同じ。起動時は設定画面を自動で開く）
  （設定の読み込みに失敗したときも同じくタブを出さず、「API設定の読み込みに失敗しました」と「再試行」）。設定画面から戻ると設定を読み直す（既存と同じ挙動。`docs/03_screen_design.md` §1 起動時の挙動）

├─────────────────────────────────────────┤

│ └─────────────────────────────────────┘ │
│ ┌─────────────────────────────────────┐ │
│ │ [表紙] 北海道 2026秋             >  │ │ ← 旅行（旅行の時期の新しい順。§4.2）
│ │        12枚 · 2026/10/05 〜 10/08   │ │
│ └─────────────────────────────────────┘ │
│ ┌─────────────────────────────────────┐ │
│ │ [表紙] 京都                      >  │ │
│ │        0枚 · 撮影日時なし           │ │
│ └─────────────────────────────────────┘ │
│              (以下同様...)              │
│                              [旅行を作る] │ ← 右下に浮かぶボタン
└─────────────────────────────────────────┘
```

**画面要素：**
- ヘッダー: タイトル「旅行」と設定ボタン（段階3で設定ボタンの左に「カテゴリ」のアイコンを足したが、2026-10-24 にカテゴリの画面ごと消した。§5.2）
- 送信の進み具合バナー（§4.7）
- 先頭の行「旅行に属さない写真」: 枚数（`GET /api/trips` の `unassignedPhotoCount`）。タップで旅行に属さない写真画面へ。
  この行は旅行ではないので、編集・削除のメニューは無い
- 旅行の一覧: `GET /api/trips` が返す順（旅行の時期の新しい順。最初の撮影日時の新しい順で、撮影日時のある写真が無い旅行は先頭に作成日時の新しい順。[05 §5.9](./05_api_design.md#59-get-apitrips)。要件 5.1「新しい旅行が上」）。各行は表紙（最初の写真のサムネイル。無いか読めなければアイコン）、
  旅行名（1行。はみ出す分は省略）、枚数と撮影の期間（`photoCount`・`firstTakenAt`・`lastTakenAt`）。タップで旅行詳細画面へ
- 「旅行を作る」ボタン（右下に浮かぶ）: 旅行の作成ダイアログ（§4.3）

**一覧以外の表示：**

| 状態 | 表示 |
|---|---|
| 読み込み中 | 「旅行一覧を読み込み中...」 |
| 旅行が0件 | 先頭の行は出す。その下に「まだ旅行がありません」「「旅行を作る」から最初の旅行を作りましょう」 |
| 一覧の取得に失敗 | 「エラーが発生しました」、エラーの文言（`ApiException` 以外の失敗では「旅行一覧の読み込みに失敗しました」）、「再試行」ボタン |
| 一覧が出ている状態での読み直しに失敗 | 一覧を出したまま、エラーの文言をスナックバーに出す（下に引っ張れば読み直せる）。読み直しの間も今の一覧を出したままにする |

旅行一覧と未所属の枚数は `GET /api/trips` の1回で取る（枚数と期間はサーバが `GROUP BY` で数え、写真を全部読まない。[04 §5.1](./04_data_design.md#51-旅行一覧)）。

**一覧を読み込み直すタイミング：** 旅行詳細・未所属の画面から戻ったとき、旅行を作ったとき、送信キューの送信が一区切りついたとき（準備中・送信中の写真が無くなったとき。枚数が変わるため。§4.7。ただし、その区切りで新しく入った写真が無い、つまり全部失敗したか全部が別の場所に送信済みだったときは、枚数が変わらないので読み直さない）、下に引っ張ったとき。

### 4.3 旅行の作成・編集ダイアログ

```
┌─────────────────────────────────────┐
│ 旅行を作る                          │ ← 編集時は「旅行を編集」
│                                     │
│ 旅行名                              │
│ ┌─────────────────────────────────┐ │
│ │例：北海道 2026秋                │ │ ← 1行・最大100文字
│ └─────────────────────────────────┘ │
│ メモ（任意）                        │
│ ┌─────────────────────────────────┐ │
│ │                                 │ │ ← 3行・最大1000文字
│ └─────────────────────────────────┘ │
│                                     │
│              [キャンセル] [作成]    │ ← 編集時は「保存」
└─────────────────────────────────────┘
```

- 旅行名: 1行、ヒント「例：北海道 2026秋」、100文字まで入力できる。メモ: 3行、1000文字まで
- 「作成」/「保存」: 前後の空白を除いて検証する。空なら入力欄の下に「旅行名を入力してください」と出して送らない。
  通れば `POST /api/trips`（作成）または `PUT /api/trips/{tripId}`（編集）を呼ぶ。処理中はボタンが「作成中...」/「保存中...」になり押せない
  - 成功: ダイアログを閉じ、「旅行を作成しました」/「旅行を更新しました」。作成後は旅行一覧を読み込み直す。編集後は旅行詳細のタイトルを更新する
  - 失敗: ダイアログに留まり、エラーの文言（`ApiException` 以外では「旅行の保存に失敗しました」）をスナックバーに出す。入力は残る
- 「キャンセル」（ダイアログの外をタップした場合も同じ）: 何もしない

旅行の期間や枚数は入力しない（写真から導く。[04 §1.2](./04_data_design.md#12-旅行type-trip)）。タグも段階2では付けない。

### 4.4 旅行詳細画面

```
┌─────────────────────────────────────────┐
│ [<] 北海道 2026秋                   [⋮] │ ← ヘッダー（戻る・旅行名・メニュー: 旅行を編集 / 旅行を削除）
│     12枚 · 2026/10/05 〜 10/08          │ ← 枚数と期間
├─────────────────────────────────────────┤
│ ┃ 送信中 5/12                           │ ← 送信の進み具合バナー（この旅行宛ての送信があるとき）
├─────────────────────────────────────────┤
│ 1日目 10月5日（月）                     │ ← 日の見出し（撮影の日が変わるところ）
│ ┌──────┐ ┌──────┐ ┌──────┐             │
│ │      │ │      │ │      │             │ ← サムネイルのグリッド（3列。撮影日時順。下端で次のページ）
│ └──────┘ └──────┘ └──────┘             │
│ ┌──────┐ ┌──────┐ ┌──────┐             │
│ │      │ │      │ │  ⟳   │             │ ← 送信中の写真は端末の画像を半透明で表示
│ └──────┘ └──────┘ └──────┘             │
│ ┌──────┐ ┌──────┐                      │
│ │      │ │  !   │                      │ ← 送れなかった写真は「!」
│ └──────┘ └──────┘                      │
│                                         │
│                            [写真を追加] │ ← 右下に浮かぶボタン
└─────────────────────────────────────────┘
```

開くたびに `GET /api/trips/{tripId}`（枚数・期間）と `GET /api/photos?tripId={tripId}`（最初のページ）を取り直す。

**画面要素：**
- ヘッダー: 戻るボタン、旅行名、右上のメニュー（「旅行を編集」→ §4.3、「旅行を削除」→ 下記。5-5d までは「編集」「削除」で、タイムラインの項目と見分けるために 5-6 で改めた。「タイムライン」を開いているときに足す項目は §8.1）。その下に枚数と期間
- 写真のグリッド（`PhotoGrid`）: 3列の正方形のサムネイル。`GET /api/photos` が返す順（撮影日時の昇順。撮影日時が無い写真はアップロード日時の位置。[04 §5.3](./04_data_design.md#53-旅行の写真一覧)）。
  下端に近づいたら次のページを読む（§3）。サムネイルが無い写真（`thumbnailUrl` が null）は原寸をサムネイルの大きさで出す。
  タップで写真ビューア（§4.6）、長押しで複数選択モード（§4.8）
- 日の見出し（**実装済み**（写真一覧の「N日目」）。`widgets/photo_grid.dart` の `dayOneTakenAt`）: 撮影の日が変わるところに「{N}日目」「{M}月{d}日（{曜日}）」の見出しを挟み、その日の写真を見出しの下の新しい行から並べる（02 #50）。
  日は撮影日時から4時間を引いた暦の日（朝4時より前の写真は前の日）で、旅行の最初の撮影日時（`GET /api/trips/{tripId}` の `firstTakenAt`）の日を1日目に、暦の日付の差で数える（写真の無い日を挟むと 1日目の次が3日目）。
  旅行の最初の撮影日時は一覧と別に読むので、一覧より古いことがある（別の端末で写真が足された・消された直後、旅行の取得の失敗や遅れ）。一覧の撮影日時のある写真に、それより前の日の写真があれば、その一番早い日を1日目にする（0日目を出さない）。
  一番早い写真が消されたときは、旅行を取り直すまで、消えた日から残った最初の日までの日数だけ番号が大きいまま残る。古い間は、絞り込んだ一覧（早い写真を含まない）と「すべて」で同じ日の番号が違うことがある（下に引っ張ったときも旅行を取り直す。下の「一覧を読み込み直すタイミング」）。
  タイムラインの日の分け方（[04 §1.6](./04_data_design.md#16-タイムラインtype-timeline-と-timelinephotos段階5)）の既定に合わせているが、切り替えの時刻はアプリの定数（4時）で、サーバの `TIMELINE_DAY_START_HOUR` を変えても写真一覧は変わらない。
  撮影日時の無い写真は見出しを作らず、返された位置のまま前の写真と同じ見出しの下に並べる（一覧の先頭なら最初の見出しより前に、見出し無しで）。端末の画像（下記）も最後の見出しの下に並べる。続きのページで同じ日が続いても見出しを重ねない。
  旅行に撮影日時のある写真が無い（`firstTakenAt` が null）ときは見出しを出さない。旅行に属さない写真の画面（§4.5）と図鑑の項目詳細（§6.2）には出さない
- 送信キューにこの旅行宛ての項目があれば、サーバの写真の後ろに端末の画像を半透明で並べる（送信待ち・送信中・送り直し待ちは回転するアイコン、失敗は「!」）。
  一覧を読み直して既にサーバの写真として並んでいるもの（送れた写真）は、端末の画像では並べない（二重にしない）。
  一度サーバの写真として並んだ送れた写真は、その後にビューアで消したり旅行から外したりしても、端末の画像として並べ直さない。
  送れた項目は一区切りまで印を付けずに並べたままにし、一区切りで一覧を取り直してサーバの写真として並び直す（一区切りまでの間に消えてまた現れることが無いように）。
  サーバの写真の続きのページが残っている間は並べず、最後のページまで読んでから並べる（続きが届くたびに端末の画像が後ろへずれないように）。
  写真が0枚の旅行でも、並べる端末の画像があれば「まだ写真がありません」ではなく端末の画像を出す。
  準備中の写真（キューに入る前）は並べない（進み具合バナーの「写真を準備中」で分かる）。
  端末の画像はタップしても長押ししても何もしない（ビューアで開けない・選べない。§4.6・§4.8）。
  旅行に属さない写真の画面（§4.5）では、旅行を指定せずに送った項目を並べる（実装済み。PR 7e）
- 「写真を追加」ボタン: 端末のギャラリーを開く（複数選択）。選んだ写真はこの旅行宛てに送る（送り方 ①。§4.7）。
  旅行を読み込めるまでと、複数選択モードの間は出さない
- 段階3で、枚数と期間・送信の進み具合バナーの下にカテゴリの絞り込みのチップを足した（§5.3）

**一覧以外の表示：**

| 状態 | 表示 |
|---|---|
| 読み込み中 | 旅行の読み込み中は回転する印だけ。旅行を読めた後、写真の一覧を読んでいる間は「写真を読み込み中...」 |
| 0件 | 「まだ写真がありません」「「写真を追加」からギャラリーの写真を送りましょう」。サーバの写真が0枚でも、並べる端末の画像（上記）があれば出さずにグリッドで並べる。カテゴリで絞っているときの0件は §5.3 |
| 旅行の取得に失敗 | 画面全体に「エラーが発生しました」、エラーの文言（`ApiException` 以外では「旅行の読み込みに失敗しました」）、「再試行」。編集・削除のメニューは出さない |
| 写真の一覧の取得に失敗 | 旅行名・枚数・期間は出したまま、写真の部分に「エラーが発生しました」、エラーの文言（`ApiException` 以外では「写真の読み込みに失敗しました」）、「再試行」 |
| 旅行が無い（404 `TRIP_NOT_FOUND`） | 「この旅行は削除されています」と表示し、戻るボタンで旅行一覧へ（一覧は読み込み直す）。旅行名と編集・削除のメニューは出さない。写真の選択中に分かったときは選択も解き、戻る1回で旅行一覧へ戻れるようにする。写真ビューアや確認ダイアログを開いている間に分かったときは、それを閉じてから出す（ビューアが読ませた続きのページで分かったときも同じ）。分かった後に、先に出していた旅行の取得の成功が遅れて届いても、旅行名とメニュー・「写真を追加」は出し直さない。旅行の取得（開いたとき・取り直し）だけでなく、写真の一覧（`GET /api/photos?tripId=`）の先頭のページ・続きのページ・下に引っ張った読み直しのどれで分かっても同じで、写真の一覧の失敗の表示（「エラーが発生しました」・「続きを読み込めませんでした」・スナックバー）は出さない。判定は `code` で行い、`code` の違う 404 は「写真の一覧の取得に失敗」などの失敗と同じ扱い。この旅行宛ての送信の進み具合バナーは出したままにする（送れなかった写真を「閉じる」で片付けられるように。PR 7e） |

**削除：** 中の写真をどうするかを利用者が選ぶ（2026-10-12 に人間が決定）。API は `deletePhotos` を必須にしているので、写真が0枚で選択肢を出さないときも `deletePhotos=false` を載せる。

```
┌─────────────────────────────────────┐
│ 旅行を削除                          │
│                                     │
│ 「北海道 2026秋」を削除します。     │
│ 中の写真12枚はどうしますか？        │
│                                     │
│ (•) 写真は残す                      │ ← 既定
│     「旅行に属さない写真」に移ります │
│ ( ) 写真も削除する                  │
│     この操作は元に戻せません        │
│                                     │
│                 [キャンセル] [削除] │
└─────────────────────────────────────┘
```

- 枚数は `GET /api/trips/{tripId}` の `photoCount`（要件 5.1「消す前に枚数を示して確認する」）。0枚なら選択肢を出さず「「京都」を削除しますか？」「キャンセル」「削除」
- 成功の知らせの枚数は応答で決める。0枚の旅行なら括弧書きを付けず「旅行を削除しました」
- 既定は「写真は残す」（誤操作で写真が消えないように）。「写真も削除する」を選ぶと「削除」ボタンが赤くなる
- 「削除」: `DELETE /api/trips/{tripId}?deletePhotos=false|true`（選んだ方。[05 §5.12](./05_api_design.md#512-delete-apitripstripiddeletephotostruefalse)）。処理中はダイアログのボタンが押せず「削除中...」
  - 成功: 「旅行を削除しました（写真12枚は「旅行に属さない写真」に移しました）」または「旅行を削除しました（写真12枚を削除）」を表示して旅行一覧へ戻る（一覧は読み込み直す）。
    枚数は応答の `detachedPhotoCount` / `deletedPhotoCount`
  - 失敗: 確認ダイアログを開いたまま（そのまま再試行もキャンセルもできる）、エラーの文言（`ApiException` 以外では「旅行の削除に失敗しました」）をスナックバーに出す。旅行詳細も閉じない。404 なら成功と同じ扱い（既に無い）
- この旅行宛ての送信が進行中（準備中・送信待ち・送信中・送り直し待ちの写真がある）なら、削除のダイアログの前に「送信中の写真があります。送信を止めて削除しますか？」（「キャンセル」「削除」）を出す。
  この旅行宛ての写真が失敗しているだけ（自動では送り直されない）なら確かめず、そのまま削除のダイアログを出す。
  「キャンセル」なら何もしない。「削除」なら上の削除のダイアログへ進み、そこで削除を確定したときに、送信キューのこの旅行宛ての項目（準備中・送信待ち・送り直し待ち・失敗）を取り消してから削除する
  （削除のダイアログで「キャンセル」したら送信は続ける。取り消しは、確定した時点の写真（準備中・送信待ち・送信中・送り直し待ち・失敗）だけに効く。削除が失敗しても取り消した写真は戻らず（選び直せば送れる）、その後にこの旅行へ追加した写真は送る。準備中の写真は残りの準備をやめ、「写真を準備中」も出さない）。取り消した写真は送らず（準備中の写真は準備が済んでも送らず、送り直し待ちの写真は待ちが過ぎても送り直さない）、失敗にも数えず、完了の知らせにも数えない。
  この旅行宛てに一区切りの前に送れていた写真も、完了の知らせに数えない。
  送信中の要求は止められないので、その結果は知らせない（送れても失敗しても数えない）。結果を待つ間も、その写真はグリッドに並べず、進み具合バナーにも送信中にも数えない（削除が失敗して旅行詳細に留まっても残らない。実装済み。PR 7e）。
  それでも削除と重なって届いた写真は消えないが、段階3の掃除のタイマーが未所属に戻すまでどの一覧にも出ない（まれなので許容。[04 §7.3](./04_data_design.md#73-旅行の削除と重なった送信move)）

見出し（枚数・期間）の取り直しが重なったときは、最後に出した取得の結果だけを使う（先に出した取得が遅れて届いても、成功でも失敗でも、新しい表示を覆さない。旅行が無い 404 は、どの取得で分かっても「この旅行は削除されています」にする）。

**一覧を読み込み直すタイミング：** 写真ビューアから戻ったとき（削除したかどうかによらない。複数選択の操作の後と同じく、先頭のページから読み直し、見出しの枚数・期間も取り直す。ビューアを開いている間に別の端末で増えた写真も出る）、複数選択の操作が完了したとき（見出しの枚数・期間も取り直す。§4.8）、送信が一区切りついて、この旅行宛ての写真が1枚以上送れていたとき（複数選択の操作の後と同じく、先頭のページから読み直し、見出しの枚数・期間も取り直す。§4.7）、下に引っ張ったとき（写真の一覧を先頭のページから読み直すのと同時に、見出しの枚数・期間も取り直す。見出しの取り直しに失敗しても前の値のまま出し、写真の一覧は読み直す。見出しを取り直すのは写真一覧の「N日目」で実装済み）。

### 4.5 旅行に属さない写真画面

旅行詳細画面と同じ部品で、次の点だけ違う。

- ヘッダーは「旅行に属さない写真」で、メニュー（編集・削除）は無い。枚数だけを出す（期間は出さない。枚数は `GET /api/trips` の `unassignedPhotoCount`）
- `GET /api/photos?tripId=none` をページで取る
- 「写真を追加」は旅行を指定せずに送る（送り方 ②。`tripId` のパートを省く）。進み具合バナーは、旅行を指定せずに送った写真だけを数える（§4.7）
- グリッドの後ろに端末の画像で並べるのは、旅行を指定せずに送った写真だけ（旅行宛ての写真は並べない。並べ方は §4.4 と同じ）
- 日の見出し（§4.4）は出さない（1日目の基準になる旅行が無いため。[02 §5](./02_design_overview.md#5-人間に決めてもらう点推奨付き) #50。実装済み。写真一覧の「N日目」）
- 0件の表示は「旅行に属さない写真はありません」「「写真を追加」で送った写真は、あとから旅行に入れられます」（並べる端末の画像があれば出さない。§4.4 と同じ）
- 複数選択の操作に「旅行から外す」は無い（「旅行に入れる」と「削除」だけ）。「旅行に入れる」のダイアログはすべての旅行を出す
- 複数選択の操作の後は、写真の一覧と一緒に枚数も `GET /api/trips` で取り直す（開いたときの枚数は旅行一覧から受け取る）。
  枚数の取り直しに失敗したら、枚数は前の値のまま出す（写真の一覧は読み直す。操作の知らせは出ているので、失敗の知らせは足さない）。
  送信が一区切りついて、旅行を指定せずに送った写真が1枚以上送れていたときと、写真ビューアから戻ったとき（削除したかどうかによらない）も、同じく写真の一覧と枚数を取り直す（§4.7）

### 4.6 写真ビューア

**実装済み**（PR 7d。`screens/photo_viewer_screen.dart`。送信中・送信失敗の写真の扱いは PR 7e）。

```
┌─────────────────────────────────────────┐
│ [<]                      [印][削除] │ ← 半透明のバー（タップで表示・非表示）。[印] は解析を頼む印だけのボタン（段階3。C-2 からカテゴリで印と説明が変わる。§5.1・§5.4。その他の写真には出さない。§5.6）
│                                         │
│                                         │
│              原寸の画像                 │ ← 左右のスワイプで前後の写真。ピンチで拡大
│                                         │
│                                         │
├─────────────────────────────────────────┤
│ 2026年10月5日 12:30                     │ ← 撮影日時（無ければ「撮影日時なし」）
│ 北海道旭川市                            │ ← 地名。無ければ緯度・経度「43.7700, 142.3600」、
│                                         │    位置情報が無ければ「位置情報なし」
│ 段階3: [風景 ▼]  段階4: サクラ >        │ ← 段階3以降（§5・§6）。カテゴリは押すと選び直せるボタン（C-1。§5.6）
└─────────────────────────────────────────┘
```

- グリッドのサムネイルをタップすると、その写真から開く（複数選択モードの間はタップで選択が切り替わり、ビューアは開かない。§4.8）
- 開いた一覧（旅行詳細・未所属）の写真を、一覧と同じ順で左右にスワイプして見られる（`PageView`）。左へ払うと次の写真、右へ払うと前の写真。原寸は `imageUrl`、表示までの間はサムネイルを出す（`thumbnailUrl` が null なら何も出さない）。原寸を読めない（SAS の期限切れの 403 など）ときは「画像を読み込めません」を出す（戻れば一覧が新しい URL で読み直される）。
  一覧がまだ読んでいないページの写真は、読み込んだ末尾の写真まで来たときに一覧が次のページを読む（ビューアは一覧の読み込み済みの配列を共有する。グリッドを下端まで送っていなくても、ビューアから読ませる）。
  最後のページまで読んでいれば、末尾でそれ以上進まない
- 画面をタップすると上のバーと下の情報の表示・非表示が切り替わる
- ピンチで拡大できる。拡大している間は左右のスワイプで前後に移らず、画像を動かす
- 下の情報は2行（段階3でカテゴリと分類の状態の行を、段階4で図鑑の項目へのリンク・コメント・「コメントを編集」の行を足す。§5.1・§6.3）。
  - 撮影日時（§3 の表記「2026年10月5日 12:30」。無ければ「撮影日時なし」）
  - 場所: 地名（`location.placeName`）があれば地名。地名が無く緯度・経度があれば「緯度, 経度」を小数4桁に丸めて出す（足りない桁は0で埋める。例 `43.77` / `142.36` は「43.7700, 142.3600」）。
    位置情報が無ければ（`location` が null）「位置情報なし」。利用者が解析を頼むときに直した地名（緯度・経度の無い撮影地も。C-2。§5.4）も同じく地名を出す
- 削除: 上のバーの「削除」で確認ダイアログ「写真を削除」「この写真を削除しますか？\nこの操作は元に戻せません。」「キャンセル」「削除」。
  「削除」で `DELETE /api/photos/{photoId}`。処理中はダイアログのボタンが押せず「削除中...」になり、外のタップ・戻る操作でも閉じない。
  成功なら確認ダイアログを閉じて「写真を削除しました」を出し、一覧の読み込み済みの写真からも除いて、次の写真へ移る（次の写真が無い、つまり一覧の末尾の写真なら一覧へ戻る。知らせは一覧に戻っても出たまま）。
  「一覧の末尾」は読み込み済みの末尾ではなく、続きのページが無いときの末尾。読み込み済みの写真を使い切っても続きがあれば、一覧に続きを読ませて、届いたら次の写真へ移る。
  削除で後ろの写真が今の位置に詰まり、それが読み込み済みの末尾になったときも、一覧に続きを読ませる（スワイプで末尾に来たときと同じ）。
  失敗なら確認ダイアログを開いたまま（そのまま再試行もキャンセルもできる）ビューアに留まり、エラーの文言（`ApiException.userMessage`。`ApiException` 以外では「写真の削除に失敗しました」）をスナックバーに出す。写真は一覧に残る。
  404 `PHOTO_NOT_FOUND`（別の端末で先に消されたなど）なら成功と同じ扱い（判定は `code` で行い、封筒の無い 404 は失敗と同じ扱い。§4.8 の複数選択の削除と同じ）
- 戻ると、開いた画面（旅行詳細・未所属）が写真の一覧と見出しの枚数を読み直す（削除したかどうかによらない。§4.4・§4.5）
- 開いている間に旅行が無い（404 `TRIP_NOT_FOUND`）と分かったら、ビューアを閉じて旅行詳細の「この旅行は削除されています」を出す（§4.4）
- 送信中・送信失敗の写真（端末にしか無いもの）はビューアで開けない（タップしても何も起きない）

### 4.7 写真の追加と送信の進み具合

**実装済み**（PR 7a・7b・7c。`widgets/add_photos_button.dart`・`services/upload_queue.dart`・`utils/photo_metadata.dart`・`widgets/upload_banner.dart`）。
PR 7a: 写真を選ぶ、準備のハッシュと EXIF、同時 2 本の送信、201 の扱い、進み具合バナーの「送信中」と失敗の行・「送り直す」「閉じる」、完了の知らせまで。
PR 7b: 準備が済んだ順に送ることと準備中の表示、自動の送り直し、404、200（別の場所）と完了の知らせの補足、失敗の理由の文言。
PR 7c: 準備のサムネイルと地名、送信の `thumbnail`・`placeName` のパート。

**写真を選ぶ：** 「写真を追加」で `image_picker` の `pickMultiImage()` を開く（既存と同じ画質85・最大1920px。
縮小しても同じ写真から同じハッシュになることは、2026-10-14 に SC-03K で確かめた（`docs/09_backlog.md`「段階2の結果」）。[02 §6](./02_design_overview.md#6-リスク)）。
選ぶ画面を開いてから写真を受け取るまでの間は、「写真を追加」のボタンを「写真を読み込み中...」（回転する印つき、灰色）に替えて押せなくする。その間に選択モードに入って抜けても、受け取るまでは「写真を読み込み中...」のまま（受け取った後の準備の間は「写真を追加」に戻り、押せる）。
写真を選ぶ部品は、選んだ写真を1枚ずつ縮小してから返すので、300枚では受け取るまで10分ほどかかる（2026-10-17、SC-03K。その間に何も出ないと、止まったように見える）。
選ばずに閉じたら何もしない（ボタンは元に戻す）。読み込みに失敗したら「画像の読み込みに失敗しました」。
選んだうちの一部だけが読めなかったときも同じ知らせを出し、読めた写真は送る（読めた写真まで送らずに捨てない）。

**準備：** 選んだ各ファイルについて、選んだ順に1枚ずつ次を行う。ハッシュと EXIF は別の isolate（`compute`）で、サムネイルと地名はその後にメインの isolate で行う
（どちらも端末の機能（プラグイン）を使い、プラグインは別の isolate から呼べないため）。その間はバナーに「写真を準備中... 3/12」
（準備を終えた枚数/選んだ枚数。サムネイルと地名まで済んだ写真を準備を終えたと数える。読めなかった写真も準備を終えた枚数に数える。準備中の選択が複数あれば、その画面が数える宛先の分を合計する）。

| 処理 | 中身 | パッケージ |
|---|---|---|
| ハッシュ | ファイルのバイト列の SHA-256（16進・小文字）→ `photoId` | `crypto` |
| EXIF | `DateTimeOriginal` → `takenAt`（`YYYY-MM-DDTHH:mm:ss`。無ければ null）、GPS → 緯度・経度（度・分・秒を10進の度に直す。南緯・西経は負。片方しか読めなければ両方 null。無ければ null）。EXIF を読めなくても送信は止めない | `exif` |
| サムネイル | 長辺 320px・画質 70 の JPEG（横長は 320×240 のように、縦長は 240×320 のように）。プラグインは幅・高さとも指定の長さを下回らない範囲で縮めるので、画像の縦横（ヘッダから読む）から短辺を「長辺 320 に合わせた長さ」に換算し、幅・高さの両方にその値を指定する（両方に 320 を指定すると短辺が 320 になる。縦横で別の値を指定すると、プラグインが EXIF の向きで縦横を入れ替えたときに長辺が 320 を超える）。作れなければ（画像を読めない・圧縮に失敗する）サムネイル無しで送る（送信は止めない） | `flutter_image_compress` |
| 地名 | 緯度・経度があれば、小数3桁に丸めた座標をキーに端末内のキャッシュを引き、無ければ端末の Geocoder で引いて都道府県＋市区町村にする（片方だけならその分だけ、どちらも空なら null）。失敗・空の結果・5 秒の時間切れは null（送信は止めない）。キャッシュに残すのは引けた地名だけ | `geocoding`（[06 §4.2](./06_processing_design.md#42-段階2端末)） |

準備が済んだ順に `UploadQueue` に入れ、全部の準備を待たずに送り始める。項目は `{ file, photoId, tripId?, takenAt, latitude, longitude, placeName, thumbnail }`。

**送信：** `UploadQueue` が同時 2 本まで `POST /api/photos` を呼ぶ（[05 §5.1](./05_api_design.md#51-post-apiphotos)。送るパートは [05 §8](./05_api_design.md#8-クライアントmobilelibservicesapi_servicedartに足すメソッド)。
撮影日時・緯度・経度・サムネイル・地名が無ければそのパートを省き、旅行に属さない写真の画面から送るときは `tripId` を省く。地名は緯度・経度を送るときだけ送る）。
画面を移っても続く（`AppRoot` が持つ）。アプリを終了すると送信待ちは失われる（端末に残さない）。
設定（API キー・エンドポイント）を変えたときも、送信待ち・失敗の写真は捨てる（前の設定の宛先には送らない。送信中の要求の結果も知らせない）。選び直せば送れる。

| 応答 | 扱い |
|---|---|
| 201 | 完了。準備中の写真も送信中の項目も無くなった（一区切りついた）ときに、送れた写真の宛先の画面（旅行詳細・未所属）と旅行一覧が一覧を読み込み直す（1枚ごとには読み直さない。数百枚の送信で取得とグリッドの作り直しが同じ数だけ起き、スクロール位置も先頭に戻るため） |
| 200（既存） | 完了。応答の `tripId` が送った宛先と違えば、その写真を「送信済み（別の場所）」として数える（宛先の一覧は変わらないので、その宛先の画面は読み直さない） |
| 0（通信失敗。応答が 60 秒返らない時間切れを含む）/ 429 / 503 | 2秒 → 4秒 → 8秒の間隔（失敗を受けてから数える）で最大 3 回送り直す。それでも失敗なら「失敗」。送り直しを待つ間も送信中として数える（バナーは「送信中」のまま、同時 2 本の枠もふさいだまま、一区切りにもならない）。429 は封筒の無い応答（Functions ランタイムの「Too Busy」）も含む。時間切れが無いと、通信が固まったときに送信中のまま枠がふさがり、送り直しも区切りも来ない |
| 404 `TRIP_NOT_FOUND` | 宛先の旅行が消えている。残りの同じ宛先の項目（まだ送っていないものと、一時的な失敗の後で送り直しを待っているもの）も送らずに「失敗」にし、「旅行が見つかりません」。その後に準備が済んだ同じ宛先の写真も、送らずに失敗にする（送っても同じ結果になる。数百枚を選んだときに無駄な要求を送らない）。消えた宛先は、その宛先を数えている画面で「送り直す」を押すまで覚えている（一区切りや「閉じる」の後に同じ旅行へ選び直した写真も送らずに失敗にする。「送り直す」を押すと忘れて送る） |
| その他（400・413・415・500・502） | 「失敗」。文言は `ApiException.userMessage` |

**進み具合バナー：** 旅行一覧・旅行詳細・未所属の画面上部に、準備中の写真かキューの項目があるときだけ出す。

```
┃ 写真を準備中... 3/12                          ← 準備中の写真があるとき（送信中・失敗の行より優先する）
┃ 送信中 5/12                                   ← 送信中（完了数/全体）
┃ 2枚を送信できませんでした（旅行が見つかりません）  [送り直す] [閉じる] ← 失敗があり、送信中の項目が無いとき
```

- 準備中の写真があれば、送信中の項目や失敗した項目があっても準備中の行だけを出す（準備が済んでから送信中・失敗の行に替わる）
- 失敗の行には、理由を括弧で添える。理由はその画面のバナーが数えている失敗した項目のうち、最後に失敗したものの文言（404 `TRIP_NOT_FOUND` は「旅行が見つかりません」、それ以外は `ApiException.userMessage`。`ApiException` 以外は「写真の送信に失敗しました」）

- 「送り直す」: 失敗した項目を再びキューに入れる（準備はやり直さない。0 / 429 / 503 の自動の送り直しも改めて 3 回まで行う）。その画面のバナーが数えている項目だけが対象
- 「閉じる」: 失敗した項目をキューから消す（端末の写真は消えない。選び直せば送れる）。その画面のバナーが数えている項目だけが対象
- 準備中の写真も送信中の項目も無くなったら、送れた分を「12枚を送信しました」とスナックバーで出す（送れた分が 0 枚なら出さない）。
  準備中の写真が残っている間は、先に送れた分があっても知らせない（選んだ写真の途中で知らせて、残りの分でもう一度知らせることはしない）。
  枚数は宛先を問わずその区切りで送れた全部で、どの画面にいても出す（送信を始めた画面を閉じていても出る。`AppRoot` が出す）。
  失敗が無ければバナーを消す。失敗があればバナーは失敗の行（「2枚を送信できませんでした」）に替わり、「送り直す」か「閉じる」まで残る。「送信済み（別の場所）」があれば
  「12枚を送信しました（1枚は送信済みでした。別の旅行か、旅行に属さない写真にあります）」（12枚には送信済みの1枚も含む）
- 旅行詳細では、その旅行宛ての項目だけを数える。旅行に属さない写真の画面では、旅行を指定せずに送った項目だけを数える。旅行一覧では全体を数える
  （数える項目が無い画面にはバナーを出さない。例: 京都宛ての送信中に北海道の詳細を開いても出ない）。準備中の写真も同じく宛先で数える
  （京都宛ての写真の準備中に北海道の詳細を開いても「写真を準備中」は出ず、旅行一覧には出る）
- 旅行詳細で旅行が無い（404 `TRIP_NOT_FOUND`）と分かって「この旅行は削除されています」にした後も、その旅行宛ての項目のバナーは出したままにする（失敗の行の「閉じる」で片付けられる。§4.4）
- 旅行詳細で旅行を削除したときは、その旅行宛ての送信を取り消す（取り消した写真は送らず、失敗にも完了の知らせにも数えない。§4.4 の「削除」）

### 4.8 複数選択と、旅行への出し入れ・削除

グリッドの長押しで複数選択モードに入る。長押しした写真が選ばれた状態で入る（「1枚を選択中」）。

```
┌─────────────────────────────────────────┐
│ [×] 3枚を選択中   [表示中をすべて選択]  │ ← ヘッダーが置き換わる
├─────────────────────────────────────────┤
│ ┌──────┐ ┌──────┐ ┌──────┐             │
│ │  ✓   │ │      │ │  ✓   │             │ ← 選んだ写真にチェック
│ └──────┘ └──────┘ └──────┘             │
│              (以下同様...)              │
├─────────────────────────────────────────┤
│ [旅行に入れる] [旅行から外す] [削除]    │ ← 下の操作バー（未所属の画面では「旅行から外す」が無い。図鑑の項目詳細は「削除」だけ。§6.2）
└─────────────────────────────────────────┘
```

- 見出しは「N枚を選択中」と「×」「表示中をすべて選択」に替わる（幅 360dp の端末で「300枚を選択中」が入りきらないときは、切らずに文字を縮めて出す）（旅行名と編集・削除のメニューは出ない）。選んだ写真には読み上げでも「選択中」の状態が付く（選択モード中は選んでいない写真も「選択されていない」と読み上げる。選択モードの外では、サムネイルに選択の状態を付けない。読み上げが全部のサムネイルを「未選択」と読まないように）
- タップで選択を切り替える。「表示中をすべて選択」で読み込んだ写真を全部選ぶ（一覧はページで読むので、まだ読み込んでいない続きは入らない。続きも選ぶには下まで送ってから押す。文言はこの範囲が分かるように「表示中を」とした（2026-10-17 に人間が決定。全部を読み込んでから選ぶ形は、100枚を超える選択がまれなので割に合わない）。送信中・失敗の写真は選べない）。「×」か端末の戻る操作で解除
  （端末の戻る操作でも画面は閉じない。解除すると選んだ写真も外れ、見出しが元に戻り、下の操作バーが消える）
- 選んだ枚数が 0 になっても選択モードのまま（「×」か戻る操作で抜ける）
- 操作は選んだ写真が 1 枚以上のときだけ押せる
- 操作の後の「一覧を読み込み直す」は、先頭のページから読み直す（「写真を読み込み中...」が出て、スクロール位置も先頭に戻る。下に引っ張ったときのように今の一覧を残したままにはしない）
- 各ダイアログは、送っている間（移動・削除の要求の応答を待つ間）は「キャンセル」と実行のボタンを押せず、外のタップ・戻る操作でも閉じない。
  旅行を選ぶダイアログでは、旅行の行と「新しい旅行を作る」も押せない（送った先と選んでいる旅行が食い違わないように。作成ダイアログを重ねると、送り終えて閉じるときに取り違える）。
  実行のボタンは「入れています...」「外しています...」「削除中...」に替わる（旅行の作成・削除のダイアログと同じ。二重に送らないように）

**旅行に入れる（送り方 ③、要件 5.1.1・5.2）：** 旅行を選ぶダイアログを出す。

```
┌─────────────────────────────────────┐
│ 旅行を選ぶ                          │
│                                     │
│ ( ) 北海道 2026秋   12枚            │ ← GET /api/trips の順。今いる旅行は出さない
│ ( ) 京都             0枚            │
│                                     │
│ [+ 新しい旅行を作る]                │ ← §4.3 のダイアログを開き、作った旅行を選んだ状態にする
│                                     │
│              [キャンセル] [入れる]  │
└─────────────────────────────────────┘
```

旅行の一覧はダイアログを開くたびに `GET /api/trips` で取り直す。読み込み中は「入れる」を押せない。
読み込みに失敗したら、ダイアログの中にエラーの文言（`ApiException` 以外では「旅行一覧の読み込みに失敗しました」）と「再試行」を出す。
旅行を選ぶまで「入れる」は押せない。
「新しい旅行を作る」で作った旅行は一覧の先頭に加わり、先に別の旅行を選んでいても作った旅行の選択に替わる（そのまま「入れる」で作った旅行に入る）。

「入れる」で `POST /api/photos/move { photoIds, tripId }`。200 件を超えるときは 200 件ずつ分けて順に送る（ちょうど 200 件なら 1 回）。

- 成功: ダイアログを閉じ、「3枚を「北海道 2026秋」に入れました」。枚数は応答の `moved` の件数（分けて送ったときは合計）。
  応答の `notFound` が空でなければ「（1枚は見つかりませんでした）」を足す（例「1枚を「京都」に入れました（1枚は見つかりませんでした）」）。
  選択を解除して（選択モードを抜ける）一覧を読み込み直す。旅行詳細では見出しの枚数・期間も `GET /api/trips/{tripId}` で取り直す（未所属の画面は §4.5）。
  取り直しに失敗したら見出しは前の値のまま出す（写真の一覧は読み直す。操作の知らせは出ているので、失敗の知らせは足さない。旅行が既に無い 404 なら「この旅行は削除されています」）
- 失敗: 留まってエラーの文言（`ApiException` 以外では「写真の移動に失敗しました」）。選択は残る（ダイアログで選んだ旅行も選んだまま）。分けて送った途中で失敗したら、送れた分は入っている（押し直すと残りが送られる。同じ写真を再び送っても同じ結果になる）。
  押し直して成功したら、出ている失敗の知らせを閉じてすぐに成功の知らせを出す

**旅行から外す：** 確認ダイアログ「旅行から外す」「3枚を旅行から外しますか？\n写真は「旅行に属さない写真」に移ります。」「キャンセル」「外す」。
「外す」で `POST /api/photos/move { photoIds, tripId: null }`（`tripId` のキーは省かずに `null` を送る。省くとサーバは 400）。成功なら「3枚を旅行から外しました」（枚数は `moved` の件数）。`notFound`・200 件ずつ分けて送ること・成功後の読み直し・失敗の扱いは「入れる」と同じ（失敗したら確認ダイアログに留まる）。

**削除：** 確認ダイアログ「写真を削除」「3枚の写真を削除しますか？\nこの操作は元に戻せません。」「キャンセル」「削除」。
「削除」で `DELETE /api/photos/{photoId}` を 1 枚ずつ順に呼ぶ（同時 2 本まで）。404 `PHOTO_NOT_FOUND`（別の端末で消されたなど）は成功と数える（封筒の無い 404 は失敗と数える）。
1 枚が失敗しても残りは続ける。全部終わったら確認ダイアログを閉じ、「3枚を削除しました」、失敗があれば「2枚を削除しました（1枚は削除できませんでした）」
（全部が失敗しても「0枚を削除しました（3枚は削除できませんでした）」で閉じる。削除では確認ダイアログに留まらない）。
選択を解除して一覧を読み込み直す（消せなかった写真は一覧に残る）。見出しの枚数の取り直しは「入れる」と同じ。

**画面要素：**
- ヘッダー: 戻るボタンとタイトル「設定」
- API設定:
  - APIキー: 伏せ字で表示し、右端のボタンで表示・非表示を切り替える。ヒント「Azure Functions のAPIキーを入力」、
    補足「Azure Portal で取得したFunction Keyを入力してください」

  - 接続テストの結果: 接続テストの後に「接続成功」または「接続失敗」を表示する。APIキーかエンドポイントを編集すると消える
- アクションボタン: 「接続テスト」「保存」「設定をリセット」
- アプリ情報: アプリ名「SnapPlant」、バージョン「1.0.0」、開発者「SnapPlant Team」（固定の表示）

開くと保存済みの値を入力欄に入れる。APIキーもエンドポイントも、未保存なら空（エンドポイントの既定値は無い）。読み込み中は「設定を読み込み中...」を表示し、
読み込みに失敗すると「設定の読み込みに失敗しました」を表示する。

**保存：**

入力を検証し、通らなければ入力欄の下にエラーを表示して保存しない。

| 入力欄 | 条件 | 表示 |
|---|---|---|
| APIキー | 空（空白だけの場合を含む） | APIキーを入力してください |
| APIキー | 前後の空白を除いて10文字未満 | APIキーが短すぎます |
| APIエンドポイント | 空（空白だけの場合を含む） | エンドポイントを入力してください |
| APIエンドポイント | スキームが無い、またはスキームが `http` で始まらない | 有効なURLを入力してください（http://またはhttps://） |
| APIエンドポイント | URL として解釈できない | 有効なURLを入力してください |

検証を通れば、前後の空白を除いて保存し（APIキーは端末の安全な保存領域、エンドポイントは通常の設定領域）、
「設定を保存しました」を表示して元の画面へ戻る（戻った後の扱いは §4.1）。
保存に失敗した場合は「設定の保存に失敗しました」を表示して画面に留まる。処理中は保存ボタンが「保存中...」になり押せない。

**接続テスト：** 宛先・成功と失敗の表示・失敗の文言を原因で分けないことは §6.4。入力欄の検証はせず、入力中の値（保存前の値）で確かめる。
設定は保存しない。処理中はボタンが「テスト中...」になり押せない。

**設定をリセット：**

```
┌─────────────────────────────────────┐
│ 設定をリセット                      │
│                                     │
│ すべての設定がリセットされます。    │
│ この操作は元に戻せません。          │
│                                     │
│             [キャンセル] [リセット] │
└─────────────────────────────────────┘
```

- 「リセット」: 保存済みの設定をすべて消し、入力欄を APIキー・エンドポイントとも空にして「設定をリセットしました」を表示する。
  画面には留まる。保存ボタンを押さなくても、この時点で保存済みの設定は消えている。
  失敗した場合は「設定のリセットに失敗しました」を表示する
- 「キャンセル」（ダイアログの外をタップした場合も同じ）: 何もしない

**戻る：** 保存せずに戻ると、入力した変更は保存されない（リセットだけは既に反映されている）。
戻った画面は保存されている設定を読み直す（§4.1）。リセットしてから保存せずに戻った場合は APIキーもエンドポイントも消えているので、
「API設定が完了していません」の表示になり、リセット前の APIキーとエンドポイントでは通信しない。設定画面は自動では開き直さない。

### 5.1 写真ビューアへの追加

**実装済み**（3-4a。`screens/photo_viewer_screen.dart`、表示名は `utils/photo_category.dart`。状態の表示を `step` で分けるのは 4-3c）。
**実装済み**（C-1）: カテゴリを押せるボタンにし、`other` を「その他」と出し、カテゴリの無い写真に「カテゴリを選ぶ」を出すこと（下の最初の項目。押した後は §5.6）と、上のバーの「やり直す」をその他の写真に出さないこと・分類と合わない写真の案内の横に「やり直す」を出さないこと（3つ目の項目）。
**実装済み**（C-2。`screens/photo_viewer_screen.dart` の `_analysisButton`、言い方は `widgets/retry_processing_dialog.dart` の `analysisRequestOf`）: 上のバーの解析を頼むボタンを、文字の「やり直す」から、カテゴリで印と説明が変わる印だけのボタンにしたこと（3つ目の項目。[02 §5](./02_design_overview.md#5-人間に決めてもらう点推奨付き) #53）。

- 下の情報に**カテゴリ**（写真の `category` 欄。`植物` / `食べ物` / `風景` / `その他`）。C-1 から、カテゴリは押すと選び直せる枠付きのボタン（文字の後ろに下向きの印）で出す（§5.6）。
  表示名はアプリが持つ（`plant` 植物・`food` 食べ物・`landscape` 風景・`other` その他。知らないキーはキーのまま出す）。図鑑のタブ（§6.1）だけは `GET /api/catalog/kinds` から作るが、
  カテゴリの表示名はアプリの表のまま（API を読めないときも出せる。種類を足すときに見直す。2026-10-18 に決定。[02 §5](./02_design_overview.md#5-人間に決めてもらう点推奨付き) #33）。
  `other` は C-1 より前は出さなかった（図鑑に載らない写真の寄せ集めで、出しても見分けの役に立たないため）が、手で直せるように「その他」と出す。
  `category` が `null` の写真（分類の前の段階2の写真・分類に失敗した写真）は「カテゴリを選ぶ」のボタンを出す。ただし分類を待っている・している（`processing.state` が `pending` / `classifying` / `identifying`）カテゴリの無い写真には、ボタンを出さない（「分類中...」だけ）。
  カテゴリは状態によらず `category` があれば出す（やり直しの間も、前回の結果のカテゴリを状態と並べて出す）
- 分類の状態（`processing.state`）: `pending` / `classifying` / `identifying` は「分類中...」、`failed` は「分類に失敗しました」と「やり直す」ボタン。`done` と `none`（段階2の写真）は状態を出さない。
  段階4（4-3c）から `processing.step` を見て、`step` が `identify` なら「識別中...」「識別に失敗しました」にする（`identify` の待ち（`pending`）も「識別中...」）。`step` が無い（段階2・3の写真）か `classify` なら今までどおり。
  サムネイルの印と読み上げ（§5.5）は `step` によらず「分類中」「分類に失敗しました」のまま。
  `failed` は自動では再試行されない（[06 §1.3](./06_processing_design.md#13-状態と失敗)）ので、「やり直す」を押すか、カテゴリを手で決める（C-1。§5.6）までこの表示のまま。
  カテゴリと状態は下の情報の行なので、上のバーと一緒に表示・非表示が切り替わる（§4.6）
- 「やり直す」ボタン: 失敗したときは下の情報の状態の横に（文字の「やり直す」で）出す（4-3c から C-1 の前までは分類と合わない写真の案内の横にも出していた。C-1 で外した。§6.3）。どの状態でも（`none` の段階2の写真も）、上のバーの「削除」の左の、解析を頼むボタンから頼める。どちらもやり直しダイアログ（§5.4）を開く。
  上のバーのボタンは C-2 から印だけ（C-2 の前は文字の「やり直す」）で、印と説明（長押しで出る・読み上げられる文。ダイアログの題と同じ）は今の写真のカテゴリで決まる（§5.4 の表）: 植物（分類が済んでいる）は虫眼鏡の印（`Icons.search`）で「植物を調べる」、食べ物・風景（分類が済んでいる）はメモの印（`Icons.edit_note`）で「コメントを書いてもらう」、カテゴリの無い写真と分類が済んでいない写真は回る矢印の印（`Icons.refresh`）で「分類し直す」。
  削除で読み込み済みの写真を使い切り、続きを待っている間は出さない（頼む写真が無い。続きの写真が出たら出す）。
  ただし C-1 から、カテゴリが `other`（その他）の写真には上のバーのボタンを出さない（調べるものが無い。カテゴリが違っていればカテゴリのボタンで直す。§5.6）。上のバーのボタンは、左右に送って見ている写真が変わるたび（一覧の写真が置き換わったときも）出す・出さないと印を決め直す
- やり直しを受け付けたら（202）、ダイアログを閉じて「受け付けました」をスナックバーに出し、応答の写真で表示を更新し（カテゴリの無い写真は「分類中...」、カテゴリが識別の対象（植物・食べ物・風景）の写真は「識別中...」になる。§5.4）、開いていた一覧の写真も同じものに置き換える（一覧に戻ったときに古い状態を出さない。サムネイルに分類中の印が付く。§5.5）
- 解析中でも、写真の削除・旅行への出し入れ・（段階4の）コメントの編集・（C-1 の）カテゴリの変更（カテゴリの無い写真の分類を待っている・している間はボタンを出さない）はできる（「解析中」で操作を止めるロックは無い。[04 §7.4](./04_data_design.md#74-ワーカーの書き込みの決まり)）

### 5.2 カテゴリ横断画面（削除した）

3-4b で、旅行一覧の上のバーの「カテゴリ」から開く画面（カテゴリの一覧と、旅行をまたいでカテゴリの写真を撮影の順に並べる画面。`screens/category_photos_screen.dart`）を入れたが、

図鑑に出ない写真（識別中・識別の失敗・分類と合わない）は、旅行詳細ではカテゴリの絞り込み（§5.3）で旅行ごとに見る。旅行に属さない写真の画面（§4.5）には絞り込みが無いので、全部の中から探す。
写真の一覧の API の `category` だけの絞り込み（旅行をまたぐ。[05 §5.2](./05_api_design.md#52-get-apiphotos)）は残す（設定画面の接続テストが使う。§6.4）

### 5.3 旅行詳細画面のカテゴリの絞り込み

**実装済み**（3-4b。`screens/trip_detail_screen.dart`）。
**実装済み**（写真一覧の「N日目」。`screens/trip_detail_screen.dart` が旅行の `firstTakenAt` を `PhotoGrid` に渡す）: 下の「日の見出し（§4.4）は絞り込んでも旅行全体の数え方のまま」。

旅行詳細画面（§4.4）の枚数と期間・送信の進み具合バナー・「写真」「タイムライン」の切り替え（§8.1。5-3a）の下に、カテゴリのチップを横一列に並べる（要件 5.4。入りきらなければ横にスクロールする）。

```
│ [<] 北海道 2026秋                   [⋮] │
│     12枚 · 2026/10/05 〜 10/08          │
├─────────────────────────────────────────┤
│ ┃ 送信中 5/12                           │ ← 送信の進み具合バナー（この旅行宛ての送信があるとき。§4.4）
├─────────────────────────────────────────┤
│ (すべて) (植物) (食べ物) (風景)         │ ← 1つだけ選べる。既定は「すべて」
├─────────────────────────────────────────┤
│ ┌──────┐ ┌──────┐ ┌──────┐             │
```

- チップの表示名と並びは §5.1 のカテゴリと同じ（植物・食べ物・風景。「その他」のチップは置かない。その写真は「すべて」で見える）。「すべて」が既定で、画面を開き直すと「すべて」に戻る
- 旅行を読み込めるまでと、旅行の取得に失敗したとき・「この旅行は削除されています」のときはチップを出さない（§4.4 の一覧以外の表示のまま）
- チップを選ぶと `GET /api/photos?tripId={tripId}&category={category}` を先頭から取り直す（継続トークンは同じ絞り込みにだけ有効。[05 §5.2](./05_api_design.md#52-get-apiphotos)）。「すべて」は `category` を付けない。
  選んでいるチップをもう一度押しても何もしない（取り直さない）
- 写真ビューアから戻ったとき・複数選択の操作の後・送信の一区切りの後の読み直し（§4.4）は、選んでいるカテゴリのまま先頭から読み直す
- 分類前の写真（`category` が `null`）と、送信中・送れなかった端末の画像は「すべて」のときだけ並べる
- 日の見出し（§4.4）は絞り込んでも旅行全体の数え方のまま（旅行の最初の日が1日目。食べ物の写真が2日目からなら、最初の見出しは「2日目」）
- ヘッダーの枚数と期間は絞り込みに関係なく旅行全体のまま。「写真を追加」は絞り込んでいても出す（送った写真は分類が済むまで、絞り込んだ一覧には出ない）
- 絞り込んだ結果が0件なら「この旅行に{表示名}の写真はありません」の1行だけ（「すべて」の0件の2行目の案内は出さない）
- 複数選択（§4.8）は絞り込んだまま使える。選択モードの間はチップを出さない（選択モードの見出しと操作バーだけにする。チップを変えると一覧が変わり、選んだ写真が見えなくなるため）

```

**実装済み**（3-4a で `step: "classify"`、4-3c でやり直す範囲（`step: "identify"`）。`widgets/retry_processing_dialog.dart`）。
**実装済み**（C-1）: やり直す範囲（「カテゴリから」「名前だけ」）をなくし、`step` を写真のカテゴリで決めること（下の最後の項目）。
**実装済み**（C-2。言い方の表は `widgets/retry_processing_dialog.dart` の `analysisRequestOf`）: 題・手がかりの欄の名前と例・頼むボタンの文言をカテゴリで変えること（下の表）と、「場所」の欄（下の「場所」の項目）。決定は [02 §5](./02_design_overview.md#5-人間に決めてもらう点推奨付き) #53 の「C-2 の画面」。

言い方（ダイアログを開いたときの写真で決める。上のバーのボタンの印と説明（§5.1）も同じ表から取る）:

| 写真 | `step` | 題（上のバーのボタンの説明） | 手がかりの欄の名前 | 欄の例 | 頼むボタン | 上のバーのボタンの印 |
|---|---|---|---|---|---|---|
| 植物（分類が済んでいる） | `identify` | 植物を調べる | 手がかり（任意） | 例：これはサクラではなくウメ | 調べる | 虫眼鏡（`Icons.search`） |
| 食べ物・風景（分類が済んでいる） | `identify` | コメントを書いてもらう | メモ（任意） | 例：朝市で食べた。うにといくらの丼 | 書いてもらう | メモ（`Icons.edit_note`） |
| それ以外（カテゴリの無い写真・`other`・分類が済んでいない写真） | `classify` | 分類し直す | 手がかり（任意） | 例：これは食べ物 | 分類し直す | 回る矢印（`Icons.refresh`） |

食べ物・風景は「調べる」と言わない（AI は利用者のメモの誤字脱字を直しながらコメントにする役。02 §5 #53）。仕組みは植物と同じ識別（`identify`）で、結果の名前は写真に残るが図鑑には載らない（§6.3）。
C-2 の前は、どのカテゴリでも題「解析をやり直す」・欄「手がかり（任意）」（例「例：これはサクラではなくウメ」）・ボタン「やり直す」だった。

- 頼むボタン: `POST /api/photos/{photoId}/process { step, hint, placeName }`（`step` は写真のカテゴリで決まる。上の表と下の最後の項目。`placeName` は「場所」の欄の値。[05 §5.7](./05_api_design.md#57-post-apiphotosphotoidprocess段階3)）。処理中は入力欄・ボタンが押せず、端末の戻る操作でも閉じない。
  202 ならダイアログを閉じ、写真ビューアが「受け付けました」を出す（§5.1）。
  失敗したらダイアログに留まり（そのまま再試行もキャンセルもできる）、入力欄の下にエラーの文言（`ApiException.userMessage`。それ以外は「解析のやり直しの受付に失敗しました」）を出す。写真は変わらない
- 「場所」（C-2）: 手がかりの欄の上に置く1行の欄（最大100文字）。写真の撮影地の地名（`location.placeName`）を入れておく（無ければ空）。欄の下に案内を1行出す:
  地名があれば「写真の撮影地を入れています。直すと撮影地も変わります」、位置情報が無ければ（`location` が `null`）「この写真には位置情報がありません。書くと撮影地として残ります」、緯度・経度だけで地名が無ければ「書くと撮影地の地名として残ります」。
  `placeName` は利用者が欄を直したとき（開いたときの地名と違うとき。空にしたときも）だけ送る。直していなければ送らない
  （手元の写真は開いたときのもので古いことがあり、送ると別の端末で直された撮影地を戻してしまう。送らなければサーバは写真を読まずに受け付ける）。
  空にして頼むと撮影地の地名が消え（緯度・経度があれば残り、ビューアは緯度・経度を出す）、手で消した印（`placeSource: "user"`）が残る。
  直して頼むと写真の撮影地の地名が変わり（`placeSource: "user"`）、受け付けた後のビューアの場所の表示（§4.6）も直した地名になる。位置情報の無い写真に書いたら、緯度・経度の無い撮影地として残り、「位置情報なし」ではなく書いた地名を出す。
  空にして頼むと撮影地の地名を消す（緯度・経度があれば緯度・経度の表示に戻り、無ければ「位置情報なし」）。
  直した地名は、続く分類・識別の AI にも撮影地として渡る（[06 §2.2・§3.1](./06_processing_design.md#31-契約)）。AI を通さずに地名だけを直す手段は今は置かない（02 §5 #53）
- 手がかりが空白だけなら、手がかり無しとして頼む（前回の手がかりは消える。[05 §5.7](./05_api_design.md#57-post-apiphotosphotoidprocess段階3)）
- 「キャンセル」: 何も頼まずに閉じる
- 手がかりの事前入力: 利用者が直したコメント（`commentSource: "user"`）があればそれを、無ければ前回の `hint` を入れておく（どちらも無ければ空）
- 受け付けた時点で写真のコメントは消え（[05 §5.7](./05_api_design.md#57-post-apiphotosphotoidprocess段階3)）、結果のコメントで置き換わる。
  ダイアログにはその旨を一行で出す（「今のコメントは AI の結果で置き換わります」）
- やり直す範囲は選ばせない（C-1。カテゴリは手で直す（§5.6）ので、やり直しで AI にカテゴリを決め直させない。[02 §5](./02_design_overview.md#5-人間に決めてもらう点推奨付き) #53）。
  写真のカテゴリが識別の対象の種類（植物・食べ物・風景。アプリの表 `photoCategories`。図鑑に載せるのは植物だけだが（§6.1）、3種類とも同じ）なら `step: "identify"`（カテゴリはそのままで、名前などを識別し直す。受け付けると「識別中...」）、
  それ以外（分類の前の `null` と `other`）と、分類が済んでいない写真（`step` が `classify` で `pending`・`classifying`・`failed`。前のカテゴリが残っていても）は `step: "classify"`（分類からやり直す。「分類中...」）で頼む（識別の対象でない写真の `identify` はサーバが 400 で断る。[05 §5.7](./05_api_design.md#57-post-apiphotosphotoidprocess段階3) の 8）。
  `other` の写真には上のバーの解析を頼むボタンを出さない（§5.1）ので、`other` で開くのは失敗したときの下の情報の「やり直す」からだけ（言い方は上の表の「分類し直す」）。
  4-3c から C-1 の前までは、識別の対象の写真に手がかりの上の「やり直す範囲」として「カテゴリから」（`classify`。既定）「名前だけ」（`identify`）を出していた

### 5.5 進み具合

**実装済み**（3-4a。`widgets/photo_grid.dart`）。

旅行詳細（と旅行に属さない写真・図鑑の項目詳細。どれも `PhotoGrid`）のサムネイルに、分類が済んでいない写真（`pending` / `classifying` / `identifying`）は右下に小さな砂時計の印を付ける。失敗した写真（`failed`）は右下に「!」。
読み上げ用のラベルは、撮影日時に「、分類中」「、分類に失敗しました」を足す。済んだ写真（`done`）と段階2の写真（`none`）には印を付けない。
一覧を下に引っ張ると最新の状態になる（自動の更新はしない）。

### 5.6 カテゴリを手で直す

**実装済み**（C-1。`screens/photo_viewer_screen.dart` のカテゴリのボタン、シートは `widgets/category_edit_sheet.dart`、選べるカテゴリと表示名は `utils/photo_category.dart` の `editableCategories`・`categoryLabel`）。
**実装済み**（カテゴリの変更で AI のコメントを消す。`widgets/category_edit_sheet.dart`）: 「保存すると、AI が書いたコメントは消えます。」の知らせ（下の4つ目の項目）と、保存すると AI が書いたコメントが消えること（「保存できたら」の項目）。
決定は [02 §5](./02_design_overview.md#5-人間に決めてもらう点推奨付き) #53（カテゴリは AI が最初に付け、直すのは手で。AI を通さない。複数の写真のカテゴリをまとめて変える操作は今は入れない）。

```
┌─────────────────────────────────────────┐
│ カテゴリを変える                        │
│ ( ) 植物                                │
│ (•) 食べ物                              │ ← 今のカテゴリを選んでおく
│ ( ) 風景                                │
│ ( ) その他                              │
│ 植物にすると、品種を調べます。          │ ← 植物以外の写真（か分類が済んでいない写真）で植物を選んだときだけ
│ 保存すると、AI が書いたコメントは消えます。│ ← AI のコメントのある写真で、保存すると送るカテゴリを選んだときだけ
│ （失敗したときのエラーの文言）          │
│                     [キャンセル] [保存] │
└─────────────────────────────────────────┘
```

- 写真ビューアの下の情報のカテゴリ（§5.1）は、枠付きのボタン（文字の後ろに下向きの印）。文言は表示名（「植物」「食べ物」「風景」「その他」）で、
  利用者が手で決めたカテゴリ（`categorySource: "user"`。[05 §3.3](./05_api_design.md#33-photo)）は末尾に「（変更済み）」（例「植物（変更済み）」。AI がもう書き換えない印。コメントの「（編集済み）」と同じ考え方）。
  カテゴリが無い写真（分類の前の段階2の写真・分類に失敗した写真）は「カテゴリを選ぶ」。分類を待っている・しているカテゴリの無い写真にはボタンを出さない（§5.1）
- ボタンを押すと、画面の下からシート（見出し「カテゴリを変える」）が出る。選択肢は「植物」「食べ物」「風景」「その他」（この順。1つだけ選べる）で、今のカテゴリを選んでおく（カテゴリが無ければどれも選んでいない）
- 植物以外の写真と分類が済んでいない写真（同じ植物でも保存すると品種を調べ始める）で「植物」を選ぶと、選択肢の下に「植物にすると、品種を調べます。」を出す（保存すると AI が品種を調べ始めるので、保存の前に知らせる）
- AI が書いたコメント（`commentSource: "ai"`）のある写真で、保存すると送るカテゴリ（今と違うもの。分類が済んでいない写真は今と同じものも）を選ぶと、選択肢の下に「保存すると、AI が書いたコメントは消えます。」を出す（サーバが消す。[05 §5.6](./05_api_design.md#56-patch-apiphotosphotoid)。利用者のコメントは残るので出さない）
- 「キャンセル」: 何も送らずに閉じる
- 「保存」: 選んだカテゴリが今のカテゴリと同じ（どれも選んでいないときも）なら、何も送らずに閉じる（送ると AI のカテゴリが手で決めたものになり、「（変更済み）」が付く。コメントの編集と同じ。§6.3）。
  ただし分類が済んでいない写真（`processing.step` が `classify` で、`pending`・`classifying`・`failed`）は、同じカテゴリでも送る（サーバが分類を止めるか失敗から出し、手で決めたカテゴリにする。送らないと後で AI の分類がカテゴリを書き換えるか、失敗のまま残る）。
  違えば `PATCH /api/photos/{photoId} { category }`（[05 §5.6](./05_api_design.md#56-patch-apiphotosphotoid)）
- 保存できたら、シートを閉じて「カテゴリを変えました」をスナックバーに出し、応答の写真で表示と開いていた一覧の写真を置き換える
  （ボタンは「{表示名}（変更済み）」。植物に変えたら品種を調べる待ちになり「識別中...」。前の識別の名前と案内、AI が書いたコメントは消える。分類に失敗していた写真は「分類に失敗しました」が消える）
- 失敗したらシートに留まり（そのまま選び直しも押し直しもキャンセルもできる）、選択肢の下にエラーの文言（`ApiException.userMessage`。それ以外は「カテゴリの保存に失敗しました」）を出す。写真は変わらない
- 保存を待っている間は、選択肢と「キャンセル」「保存」が押せず、端末の戻る操作とシートの外のタップでは閉じない（閉じると、保存されたのに表示が古いまま残る。他のダイアログと同じ）。
  シートは下へ払っても閉じない（払う操作は保存を待っている間でも閉じてしまうため。タイムラインの編集シート §8.5 と同じ）
- その他の写真には上のバーの解析を頼むボタン（C-2 の前は「やり直す」）を出さない（調べるものが無い。§5.1）。カテゴリが違っていれば、このボタンで直す
- 解析中でもカテゴリのある写真なら直せる（ロックは無い。[04 §7.4](./04_data_design.md#74-ワーカーの書き込みの決まり)）。分類が済んでいない写真で今のカテゴリと同じものを保存すると、送って分類を止める・失敗から出す（上の「保存」の決まり）

## 6. 段階4の画面（骨格）

### 6.1 図鑑タブ（種類タブ → 項目一覧）

**実装済み**（4-3a。`screens/catalog_screen.dart`、タブは `screens/home_shell.dart`。項目をタップして項目詳細を開くのは 4-3b、下のタブの「図鑑」への差し替えは 4-5 で実装済み）。
**実装済み**（B-2。`screens/catalog_screen.dart`）: 種類が1つなら種類のタブを出さずに、その種類の項目を並べること（下の細部の最初の項目）。図鑑に載せる種類は植物だけで（[02 §5](./02_design_overview.md#5-人間に決めてもらう点推奨付き) #51）、`GET /api/catalog/kinds` は植物だけを返す（[05 §5.14](./05_api_design.md#514-図鑑段階4)）ので、今はタブが出ない。

```
┌─────────────────────────────────────────┐
│ 図鑑                             [設定] │
│ [植物] [食べ物] [風景]                  │ ← 種類タブ（GET /api/catalog/kinds の順。種類が1つなら出さない）
├─────────────────────────────────────────┤
│ ┌─────────────────────────────────────┐ │
│ │ [表紙] サクラ                 [92%] │ │ ← 項目（名前・信頼度・写真の枚数）
│ │        3枚                          │ │
│ └─────────────────────────────────────┘ │
└─────────────────────────────────────────┘
```

`GET /api/catalog/entries?kind={kind}&offset=&limit=`。項目は文書ではなく、識別済みの写真をサーバが名前でまとめたもの（[04 §3.1](./04_data_design.md#31-項目は写真からまとめる)）。
信頼度・説明・表紙はその名前の写真のうち信頼度が最も高いものから来る。植物一覧画面（カード）を置き換えた（4-5）。信頼度のバッジの色分けは既存の4段階を流用。
1回に 50 件（サーバの既定）で、下端に近づいたら `offset` を進めて次のページを読む（§3 の写真の一覧と同じ出方）。
次の `offset` は読んだ件数ではなく `limit` だけ進め、`offset >= total` になったら読み切り。サーバは数えてから見出しを読むまでに写真が無くなった項目をページから外すので、読んだ件数が `limit` より少なくても続きがあることがある（[05 §5.14](./05_api_design.md#514-図鑑段階4)）。読んだ件数で進めると、次のページで同じ項目が重なる
種類タブを切り替えるたびに先頭から読み込み直す（自動の更新はしない。下に引っ張れば取り直す）。

細部（4-3a。2026-10-18 に決めた）:

- 図鑑は起動時のタブなので、アプリを開くとすぐ種類の一覧（`GET /api/catalog/kinds`）を読む（4-5 で下のタブの「図鑑」に差し替えるまでは、3つ目のタブ「図鑑（新）」を初めて開いたときに読んでいた）。種類のタブは応答の `kinds` の順で、表示名は `label`。最初のタブ（植物）の項目を読む。
  **種類が1つ（今は植物だけ）なら、種類のタブ（タブが1つだけの帯）は出さず、見出し「図鑑」と設定ボタンの下にその種類の項目を並べる**（B-2）。項目の行・0件の「{表示名}の項目はまだありません」・読み直し・続きのページは、タブがあるときと同じ。
  種類の一覧を読み込む間は、見出し「図鑑」と設定ボタンの下に「図鑑を読み込み中...」（種類のタブはまだ出さない）。
  種類のタブの文字は見出しの緑の上に出すので、選んでいるタブは白、選んでいないタブは薄い白（白の 70%）（2026-10-22。実機で、選んでいるタブの文字が背景の緑と同じ色で見えなかった）。
  種類の一覧を読めなければ「エラーが発生しました」・エラーの文言（`ApiException.userMessage`。それ以外は「図鑑の読み込みに失敗しました」）・「再試行」（「再試行」で種類の一覧から読み直す。この表示は下に引っ張っても読み直さない）
- 項目の行: 左に表紙のサムネイル（読めないときは本のアイコン。種類によらず同じ。`coverThumbnailUrl` は `null` にならない。[05 §3.3.1](./05_api_design.md#331-catalogentry段階4)）、名前、2行目に「{photoCount}枚」、右に信頼度のバッジ（「92%」。四捨五入した整数。色は植物図鑑の4段階の `AppColors.getConfidenceColor`）。
  表紙の画像のキャッシュの鍵は、旅行一覧の表紙と同じく署名（URL のクエリ）を除いた Blob の場所から作る `cover-<ホスト><パス>`（§3）。署名は読み込むたびに変わるので、URL のままだと毎回取り直す
- 読み込み中は「図鑑を読み込み中...」、項目が0件なら「{表示名}の項目はまだありません」「識別が済んだ写真が、ここにまとまります」、
  取得に失敗したら「エラーが発生しました」・エラーの文言（`ApiException.userMessage`。それ以外は「図鑑の読み込みに失敗しました」）・「再試行」。
  0件と失敗の表示も、下に引っ張れば読み直す。
  続きを読む間は一覧の下端に「読み込み中...」、続きのページの失敗は、一覧の下端に「続きを読み込めませんでした」「再試行」（写真の一覧と同じ）
- 1ページの項目がすべて外れて（上の「数えてから見出しを読むまで」）空でも、`offset < total` なら続きを読む（写真の一覧の「ページが空でもトークンがあれば続きを読む」と同じ。§3）。
  `offset >= total` で読んだ項目が0件のときだけ0件の表示にする
- 一覧を出したまま下に引っ張った読み直しに失敗したら、一覧はそのままにして、エラーの文言をスナックバーに出す（写真の一覧と同じ）。
  読み直しは先頭（`offset=0`）から読み、続きを読んでいる間に読み直したら、遅れて届いた古い続きは捨てる
- 項目をタップすると項目詳細（§6.2）。項目詳細から戻ったとき、項目詳細が最後に出した見出し（1ページ目の応答の `entry`。続きのページの応答の `entry` は使わない。§6.2）の、一覧の行に出すもの（表紙の写真〔署名を除いた場所〕・枚数・信頼度〔四捨五入する前の値〕）が、タップした行と違えば、一覧を先頭から読み直す
  （項目詳細で写真を消した、やり直しで名前が変わったなど。02 §5 #35）。項目詳細でその項目の写真が無い（1ページ目の応答が `entry: null`）と分かったときも読み直す。
  どちらも、下に引っ張ったときと同じく、読み直す間は今の一覧を出したままにし、失敗したらスナックバー。どれも同じなら読み直さない（スクロール位置を保つ。コメントを編集しただけなら行は変わらない）。
  項目詳細で一度も見出しを出せずに戻ったとき（読み込み中・取得の失敗の表示のまま戻った）は、タップした行のままとみなして読み直さない。写真ビューアから戻ったとき・削除の後の読み直しは、写真が変わったかもしれないので、読み直した見出しが出るまでは「分からない」として扱い、その読み直しが失敗したとき・終わる前に戻ったときは一覧を読み直す。
  下に引っ張った読み直しが失敗したときは、その前に出した見出しで比べる（引っ張っただけでは写真は変わらない）

4-3a から 4-5 までは、この画面を下のタブの3つ目「図鑑（新）」に置き、図鑑タブ（植物一覧画面）はそのまま残していた（2026-10-18 に決定。[02 §5](./02_design_overview.md#5-人間に決めてもらう点推奨付き) #31）。
4-5 で図鑑タブをこの画面に差し替え、3つ目のタブを消した（旧図鑑の植物は移さずに捨てると決めたので、[06 §7](./06_processing_design.md#7-今の植物図鑑の統合と廃止段階4) の手順 3 の確認は待たない。02 §5 #34）。

### 6.2 図鑑の項目詳細画面

**実装済み**（4-3b。`screens/catalog_entry_screen.dart`。写真は `widgets/photo_grid.dart` の `loadPage` に項目の詳細のページを渡して読む）。

```
┌─────────────────────────────────────────┐
│ [<] サクラ                              │
├─────────────────────────────────────────┤
│ [92%]  3枚                              │
│ 説明: …                                 │
│ 特徴: …                                 │
│ 学名: Prunus × yedoensis                │ ← kinds の fields を順に回して attributes[key] を出す
│ 科名: バラ科                            │    （無ければ「—」）
├─────────────────────────────────────────┤
│ ┌──────┐ ┌──────┐ ┌──────┐             │ ← この項目の写真（PhotoGrid。旅行をまたぐ）
│ └──────┘ └──────┘ └──────┘             │
└─────────────────────────────────────────┘
```

`GET /api/catalog/entry?kind={kind}&name={name}`（名前は URL エンコード。[05 §5.14](./05_api_design.md#514-図鑑段階4)）。写真は `continuationToken` でページで読む（§3）。写真をタップすると写真ビューアへ。
見出しの「枚数」は `entry.photoCount`（サーバが数えた総数）で、読み込んだページの枚数ではない。
見出し（名前・信頼度・説明・項目・枚数）は1ページ目の `entry` で出し、続きのページの応答の `entry` では書き換えない（読む間に見出しが入れ替わらないように。開き直すか下に引っ張れば取り直す）。
続きのページの応答が `entry: null`（読む間にその名前の写真が無くなった）なら、続きは無いものとして読み終える（出している写真と見出しはそのまま。開き直すと「この項目には写真がありません」）
項目を削除する操作は無い（項目は写真の集まりなので、写真を消すか、やり直しで名前を変えれば消える）。

細部（4-3b。2026-10-19 に決めた）:

- 図鑑の一覧（§6.1）の項目の行をタップすると開く。画面上部は項目の名前
- 見出し: 信頼度のバッジ（一覧の行と同じ「92%」）と「{photoCount}枚」、「説明」「特徴」、その種類の `fields` の順に「{label}」と値。
  説明・特徴・欄の値が無い（`null`・空・キーが無い）ときは「—」。`string[]` の値は「、」でつなぐ
- 写真は旅行をまたいで `sortAt` の順（旅行詳細と同じグリッド。ただし日の見出し（§4.4）は出さない。02 #50）。送信中の写真は並べない（まだ識別されていない）。
  長押しの複数選択の操作は「削除」だけ（どの旅行へ移すかの操作は旅行の画面で行う）
- 写真ビューアから戻ったとき・複数選択で削除したときは、見出しと写真を1ページ目から読み直す（削除や、やり直しで名前が変わって枚数が変わるため）
- 下に引っ張ると、見出しと写真を1ページ目から読み直す。読み直した結果が `entry: null` なら、下の表の「`entry` が `null`」の表示にする
- 下に引っ張った読み直しの間は今の見出しとグリッドを出したままにし、失敗したらエラーの文言（`ApiException` 以外では「項目の読み込みに失敗しました」）をスナックバーに出す（§3 の写真の一覧と同じ）。
  写真ビューアから戻ったとき・削除の後の読み直しの間は、見出しを出したまま写真の部分を「項目を読み込み中...」にし、失敗したら写真の部分を下の表の「取得に失敗」の表示にする
- 続きのページを読む間・続きの失敗の出方は §3 の写真の一覧と同じ（下端に「読み込み中...」、「続きを読み込めませんでした」「再試行」）
- 見出しは画面の高さの4割まで。説明などが長くて収まらない分は、見出しの中でスクロールする（写真のグリッドの高さを残す）
- 1ページ目の読み直しが重なっても、見出しは写真と同じ応答から出す。どの応答を採るかは次のとおり:
  写真ビューアから戻ったとき・削除の後は、写真の部分を作り直して読み直すので、それより前に始めた読み直し（引っ張った読み直しなど）の応答は成功でも失敗でも捨てる。
  同じ表示のまま読み直しが重なったとき（取得の失敗の表示で、引っ張りながら「再試行」を押したなど）は、先に成功した応答を採り、その後に届いた応答は捨てる

| 状態 | 表示 |
|---|---|
| 読み込み中 | 「項目を読み込み中...」 |
| `entry` が `null`（写真が 0 枚。やり直しで名前が変わった直後など） | 「この項目には写真がありません」「写真が削除されたか、解析のやり直しで名前が変わりました」と「戻る」。図鑑の一覧から開いたときは、戻ると（「戻る」でも端末の戻る操作でも）図鑑の一覧を読み込み直す（§6.1。見出しが一覧の行と違うときも読み直す） |
| 取得に失敗 | 「エラーが発生しました」、エラーの文言（`ApiException` 以外では「項目の読み込みに失敗しました」）、「再試行」 |

### 6.3 写真ビューアへの追加

**実装済み**（4-3c。`screens/photo_viewer_screen.dart`、コメントの編集ダイアログは `widgets/comment_edit_dialog.dart`）。
**実装済み**（B-2。`screens/photo_viewer_screen.dart`、図鑑に載る種類の表は `utils/photo_category.dart` の `isListedInCatalog`）: 図鑑に載せない種類（食べ物・風景）の識別の名前を、リンクにせず文字で出すこと（下の2つ目の項目）。
**実装済み**（C-1）: 分類と合わない写真の案内を「{カテゴリ}が写っていないようです。カテゴリを確かめてください」にし、横の「やり直す」をなくしたこと（下の3つ目の項目と、細部の「分類と合わない写真の案内」の項目）。

- コメント（AI の一言。`comment`）と「コメントを編集」。編集は入力欄のダイアログ（500文字まで）→ `PATCH /api/photos/{photoId} { comment }`。
  `commentSource: "user"` のときは「（編集済み）」と出す。AI の一言（`commentSource: "ai"`）は、カテゴリを手で変えると消える（§5.6。利用者のコメントは残る）
- 図鑑の項目へのリンク（`identification.matchesKind` が true なら `identification.name` →「サクラ >」。タップで項目詳細（§6.2）を `identification.kind`・`name` で開く）。
  リンクにするのは、識別の種類（`identification.kind`）が図鑑に載る種類（アプリの表 `isListedInCatalog`。今は植物だけ）のときだけ。
  図鑑に載せない種類（食べ物・風景。やり直しで識別した写真（C-1 の前は「名前だけ」）。[02 §5](./02_design_overview.md#5-人間に決めてもらう点推奨付き) #51）は、名前を「>」を付けない文字（白）で出し、押しても何も起きない（項目詳細を開かず、種類の一覧も読まない）（B-2）。
  アプリの表はサーバの `GET /api/catalog/kinds` に追従しない（[04 §3.2](./04_data_design.md#32-定義表-catalog_kindsapisrccatalogkindsts)）
- `identification.matchesKind: false` のときは、リンクの代わりに「{識別の種類の表示名}が写っていないようです。カテゴリを確かめてください」（例「植物が写っていないようです。カテゴリを確かめてください」。表示名は `identification.kind` から §5.1 の表で。C-1。[02 §5](./02_design_overview.md#5-人間に決めてもらう点推奨付き) #53）。
  横に「やり直す」は出さない（カテゴリはカテゴリのボタンで直す。§5.6。手がかりを付けて識別し直すなら上のバーの解析を頼むボタン（植物は「植物を調べる」。§5.4）から頼める）。C-1 の前は「分類と合わない写真です。やり直しで手がかりを付けてください」と「やり直す」だった
- 解析中（`processing.state` が `pending` / `classifying` / `identifying`）でもコメントは編集できる。自動の解析は利用者のコメントを消さない（[06 §2.3](./06_processing_design.md#23-書き込み)・[§3.2](./06_processing_design.md#32-書き込み)）。
  やり直し（§5.4）だけが置き換える

細部（4-3c。2026-10-19 に決めた）:

- 下の情報（§4.6）の、カテゴリと状態の下に置く。上から、図鑑の項目へのリンク（または分類と合わない写真の案内）、コメント、「コメントを編集」
- コメントが無ければコメントの行は出さない（「コメントを編集」は出す）。利用者が直したコメント（`commentSource: "user"`）は末尾に「（編集済み）」
- 「コメントを編集」: ダイアログ（見出し「コメントを編集」、入力欄に今のコメントを入れておく。3行・最大500文字、「キャンセル」「保存」）。
  保存中は入力欄とボタンが押せず、閉じられない。空・空白だけで保存するとコメントを消す（サーバは `null` と同じに扱う。[05 §5.6](./05_api_design.md#56-patch-apiphotosphotoid)）。
  成功したらダイアログを閉じて「コメントを保存しました」をスナックバーに出し、応答の写真で表示と開いていた一覧の写真を置き換える。
  失敗したらダイアログに留まり、入力欄の下にエラーの文言（`ApiException.userMessage`。それ以外は「コメントの保存に失敗しました」）を出す
- 項目へのリンクは「{name} >」のボタン。タップすると種類の一覧（`GET /api/catalog/kinds`）を読んでから項目詳細を開く（見出しの欄に `fields` が要るため）。
  種類の一覧を読めなければ、エラーの文言（`ApiException.userMessage`。それ以外は「図鑑の読み込みに失敗しました」）をスナックバーに出して開かない。
  種類の一覧に無い種類（種類を減らした後の古い識別など）なら、開かずに「図鑑にこの種類がありません」をスナックバーに出す（サーバは項目の詳細の種類を同じ定義表で断る。[05 §5.14](./05_api_design.md#514-図鑑段階4)）。
  ビューアから開いた項目詳細から戻るとビューアに戻る（ビューアは何も読み直さない。項目詳細から戻ったときの図鑑の一覧の読み直し（§6.1・§6.2）は、図鑑の一覧から開いたときだけ）
- やり直しを待っている間（`pending` など）も、前回の識別（`identification`）があればリンクと案内を出す（前回の結果はやり直しの結果が出るまで残る。05 §5.7）
- 分類と合わない写真の案内（「{カテゴリ}が写っていないようです。カテゴリを確かめてください」）は文字だけで、横に「やり直す」は置かない（C-1。4-3c から C-1 の前までは横の「やり直す」でやり直しダイアログ（§5.4）を開いた）
- 下の情報は画面の高さの半分まで。コメントなどが長くて収まらない分は下の情報の中でスクロールし、「コメントを編集」はスクロールの外（下の情報の下端）に置いていつも押せるようにする
- 項目へのリンクを押してから項目詳細が開くまで（種類の一覧を読む間）は、もう一度押しても何もしない（項目詳細を重ねて開かない）
- コメントを変えずに（前後の空白を除いて今のコメントと同じまま）「保存」を押したら、何も送らずにダイアログを閉じる（送ると AI のコメントが利用者のコメントになり、「（編集済み）」が付く）。図鑑に無い種類へのリンクとあわせて 02 §5 #39 で確定

### 6.4 植物図鑑の廃止に伴う画面の削除

**実装済み**（4-5。[06 §7](./06_processing_design.md#7-今の植物図鑑の統合と廃止段階4) の手順 4）。

- 植物一覧画面（`screens/plant_list_screen.dart`・`widgets/plant_card.dart`）、画像選択・コンテキスト入力画面（`screens/camera_screen.dart`）、識別結果確認画面（`screens/identification_screen.dart`）、植物詳細画面（`screens/plant_detail_screen.dart`）を削除した。
  植物の写真を撮って識別・保存する入口はアプリから無くなり、植物は旅行アルバムの写真の識別から図鑑（§6.1）にまとまる
- 下のタブの「図鑑」は図鑑画面（§6.1）になり、3つ目のタブ「図鑑（新）」は消した（§4.1）
- アプリはカメラを使わない（写真はギャラリーから選ぶだけ）ので、`AndroidManifest.xml` の `android.permission.CAMERA` を外した（2026-10-22。02 §5 #38）
- `models/plant.dart` と、`ApiService` の植物のメソッド（`uploadAndIdentifyImage`・`checkDuplicate`・`savePlant`・`getPlants`・`getPlant`・`updatePlant`・`deletePlant`）、`ApiException.isImageAlreadySaved` を削除した。アプリは植物図鑑の API（`/api/images/upload`・`/api/plants*`）を呼ばない（API は 4-6 で消す）
- **設定画面の「接続テスト」は、入力中のエンドポイントと API キー（保存前の値）で、旅行をまたぐ写真の一覧を1件だけ読んで（`GET /api/photos?category=plant&limit=1`）確かめる**（以前は `GET /api/plants`）。2xx なら届いたとみなす。
  Function Key に加えて、サーバがデータベース（とストレージ）に届くかまで確かめるため。キーが違えば 401、データベースに届かなければ 503 などで失敗になる。
  使わないもの: 図鑑の種類の一覧（定義表を返すだけで、データベースの設定が誤っていても成功する）、1件の読み取り（Cosmos の SDK がコンテナが無いときの 404 も「見つからない」にまとめる）、旅行の一覧（全部を集計して重い）。
  2xx なら結果に「接続成功」、スナックバーに「接続に成功しました」。それ以外（2xx 以外の応答と通信の失敗）は結果に「接続失敗」、スナックバーに「接続に失敗しました。設定を確認してください。」。
  失敗の文言は原因（キー・エンドポイント・サーバの障害）で分けない（どれが違うかを知らせると、キーやエンドポイントを推し量る手がかりになる。02 §5 #37）。
  キーかエンドポイントが空（空白だけを含む）なら「APIキーとエンドポイントを入力してください」で何もしない。宛先以外の振る舞いは設定画面（§4.9）

## 7. 画面遷移のパターン（段階2）

### 旅行を作って写真を送る（送り方 ①）

1. ホーム → 旅行タブ
2. 「旅行を作る」→ 旅行名を入れて「作成」
3. 一覧の旅行をタップ → 旅行詳細
4. 「写真を追加」→ ギャラリーで複数選択
5. 準備 → 送信（バナーに進み具合）。画面を移っても続く
6. 送信が一区切りつくと一覧が更新される

### 旅行を決めずに送り、あとで旅行に入れる（送り方 ②・③）

1. 旅行一覧の先頭「旅行に属さない写真」→ 「写真を追加」→ 送信
2. 送った写真を長押し → 複数選択 → 「旅行に入れる」→ 旅行を選ぶ（または「新しい旅行を作る」）→ 「入れる」
3. 旅行に属さない写真から消え、選んだ旅行に並ぶ

### 写真を見る・削除する

1. 旅行詳細 → 写真をタップ → 写真ビューア（スワイプで前後）
2. 「削除」→ 確認 → 次の写真へ（最後なら一覧へ）

### やり直し・キャンセル

- 各ダイアログの「キャンセル」（外をタップした場合も同じ）はその画面に留まる
- 複数選択モードは「×」か端末の戻る操作で解除する（選択は捨てる）
- 送信の失敗は「送り直す」で再開、「閉じる」で諦める。送った分は取り消せない（サーバの写真を消すには削除する）

**作り直しは、確かめたうえで今のタイムラインを消して一から作る。** 作る・作り直すを始めたら、やめずに最後まで進む（「やめる」を出さない）（2026-10-28 に人間が決定。それまでは作り直しの間も完成版を見せ続け、作る途中でも「やめる」で捨てられた。画面は 5-6 で、作り直しを始めたら今のタイムラインを出さない。API が始めたときに完成版を消すのは 5-6b で、どちらも実装済み）。
画面の文言では「区切り」を使わず、AI が出す場面の分け方を「タイムラインの案」と呼ぶ（2026-10-28 に人間が決定。写真を長押しして出す『ここで区切る』の説明は残す。5-6）。
**AI を使うのは、作るときと最初から作り直すときだけ。** 作り直しは手で直した文と区切りも捨てて一から作り、完成した後に区切りを直すときは AI を使わない（新しい場面は見出しなし、つなげた場面は前の場面の文が残る）（2026-10-27 に人間が決定。区切りの直しを保存するとその場で完成版に当たり、画面が読み直すのは 5-5a、作り直しで手で直した文と区切りを捨てるのは 5-5b（api）で実装済み。文言・「見出しなし」などの画面の変更と、残せなかった文の案内を消したのは 5-5c で実装済み）。

### 8.1 旅行詳細の切り替え

**実装済み**（5-3a。`screens/trip_detail_screen.dart`・`widgets/trip_timeline_view.dart`）。
**実装済み**（5-6。`screens/trip_detail_screen.dart` の `_timelineMenuItems()`、項目の中身は `widgets/trip_timeline_view.dart` の `TimelineMenu`）: 旅行詳細の上のバーのメニューのタイムラインの項目と、旅行の項目の「旅行を編集」「旅行を削除」。
**実装済み**（引っ張って読み直す。`widgets/trip_timeline_view.dart` の `_refresh()`）: 下の「タイムラインを読み込めた後は、下に引っ張ると…」。

- 旅行詳細の見出し（枚数・期間）と送信の進み具合バナーの下に「写真」「タイムライン」の切り替えを置く。既定は「写真」。旅行詳細を開き直すと「写真」に戻る。
  旅行を読み込めるまでと、旅行の取得に失敗したとき・「この旅行は削除されています」のときは切り替えを出さない（チップと同じ。§5.3）
- 「写真」は今の旅行詳細（カテゴリのチップ・グリッド・「写真を追加」）。「タイムライン」ではチップと「写真を追加」を出さない（見出しと送信の進み具合バナーは出したまま）。
  「写真」に戻すと、選んでいたカテゴリのまま写真の一覧を先頭から読み直す
- 複数選択の間は切り替えを出さない（選択モードは「写真」の中だけ）
- 「タイムライン」を選ぶたびに `GET /api/trips/{tripId}/timeline` を読む。読み込み中は「タイムラインを読み込み中...」、失敗は「エラーが発生しました」・エラーの文言（`ApiException.userMessage`。それ以外は「タイムラインの読み込みに失敗しました」）・「再試行」（押すと読み込み中に戻して読み直す）。
  404 `TRIP_NOT_FOUND` は写真の一覧と同じく「この旅行は削除されています」（§4.4）
- 下書きを作っている間（`job.state` が `pending` / `running`）は、タイムラインを開いている間だけ 5 秒ごとに `GET …/timeline/draft` を読み直す（「写真」に戻す・旅行詳細を閉じると止める。作っている間でなくなったら止める）。待ちから処理中に変わった（`pending` → `running`）だけでは表示を変えない。下書きが無くなった（完成版に入れ替わった）か、`phase` が変わったか、`job.state` が `pending` / `running` でなくなった（失敗した）ら、`GET …/timeline` を読み直す（読み込み中にはせず、読めたら表示を替える）。
  下書きの読み直しと、続けて読む `GET …/timeline` に失敗しても表示は変えず、次の回（5 秒後）に下書きからもう一度読む（404 `TRIP_NOT_FOUND` なら「この旅行は削除されています」）。
  `GET …/timeline` の読み込みや操作を始めたら、それより前に始めた読み直し・読み込みの応答は使わない（重なったら、最後に始めたものの結果だけを使う。旅行が無い 404 `TRIP_NOT_FOUND` だけは、どの応答で分かっても事実なので「この旅行は削除されています」にする）。操作の後の読み直し（「やめる」の後・409 の後・区切りの直しを当てた「もう一度」の後（§8.3））に失敗したら、上の読み込みの失敗と同じ表示（下書きの読み直しも止め、「再試行」で読み直す）
- タイムラインを読み込めた後は（まだ無い・作っている間・案ができた・完成版のどれでも）、下に引っ張ると `GET …/timeline` を読み直す。解析中の写真があと何枚かを出し直し、解析が終わっていれば「タイムラインを作る」・メニューの「タイムラインを作り直す」（写真が変わった案内の「作り直す」も。§8.3）を押せるようになる（2026-10-30 に人間が決定。開いている間は解析の進み具合を自動では読み直さない）。
  読み込み中と「エラーが発生しました」の間は引っ張っても読み直さない（「再試行」で読み直す）。操作（作る・もう一度・やめる・タイムラインを編集）を送っている間と、写真ビューアで開く写真を読んでいる間も、引っ張っても読み直さない（読み直しの応答が、操作の後や開いた画面の上に届いて、古い状態を当てたりエラーを出したりしないように）。旅行詳細の見出し（枚数・期間）は取り直さない（写真の一覧と同じ。§3）。
  読み直す間は今の表示のままにし、失敗したら表示はそのままでエラーの文言（`ApiException.userMessage`。それ以外は「タイムラインの読み込みに失敗しました」）をスナックバーに出す（写真の一覧と同じ。§3。作っている間なら 5 秒ごとの下書きの読み直しは続ける）。404 `TRIP_NOT_FOUND` なら「この旅行は削除されています」。
  引っ張った読み直しも上の「`GET …/timeline` の読み込み」に数え、それより前に始めた読み直し・読み込みの応答は使わない
- どの操作も、409 `TIMELINE_STATE_CONFLICT` を受けたら「タイムラインが変わりました。読み直しました」をスナックバーに出して読み直す。404 `TIMELINE_NOT_FOUND`（読んだ後に別の端末が下書きをやめた・書き終えた）も同じ。409 `TIMELINE_PHOTOS_PROCESSING`・`TIMELINE_NO_DATED_PHOTOS` はエラーの文言をスナックバーに出して読み直す。
  404 `TRIP_NOT_FOUND` は読み込みと同じく「この旅行は削除されています」。それ以外の失敗はエラーの文言（`ApiException.userMessage`。それ以外は「タイムラインの操作に失敗しました」）をスナックバーに出し、表示はそのまま
- 操作（作る・もう一度・やめる・タイムラインを編集）を送っている間は、タイムラインの操作のボタン（メニューのタイムラインの項目も）を押せない（二重に送らない）
- 旅行詳細の上のバーのメニューは、「タイムライン」を開いていて完成版を出していて、下書きが無いとき、「旅行を編集」「旅行を削除」の上に「タイムラインを編集」「タイムラインを作り直す」を足す（区切り線で分ける。§8.3）。「写真」を開いているとき、タイムラインを読み込んでいる間・読み込みに失敗したとき、下書きがあるときは足さない（「写真」に切り替えると外し、開き直したタイムラインが読めたら入れ直す）。旅行の項目は「編集」「削除」から「旅行を編集」「旅行を削除」に改める（タイムラインの項目と見分けるため。5-6）

### 8.2 作っている間（完成版が無いとき）

**実装済み**（5-3a。`widgets/trip_timeline_view.dart`。「区切りを確認する」（今の「案を確認する」）は 5-3b）。
**実装済み**（5-6。`widgets/trip_timeline_view.dart` の `_buildDraft()`）: 今の文言（「タイムラインの案」「案を確認する」と3つの段の名前）、待ち時間の添え書き、「やめる」を出さないこと、完成版があっても `recut` 以外の下書きならこの表で出すこと。
完成版があり、下書きが無いか、タイムラインを編集している途中（下書きの `reason: "recut"`）なら §8.3 の表示。それ以外はこの表（5-6）。作り直しを始めたら、今のタイムラインは出さずにこの表で出す（API が完成版を消すのは 5-6b から（実装済み）。それまでは完成版と `reason: "rebuild"` の下書きが両方あり、書き終えたときに完成版が置き換わる。5-6b の後も、それより前に始めた `rebuild` の下書きは同じ）。

| 状態 | 表示 |
|---|---|
| 何も無い（`timeline: null`）・解析中の写真がある（`pendingPhotoCount > 0`） | 「タイムラインはまだありません」「写真を送り終えたら、日ごと・食事ごとにまとめたタイムラインを作れます。」、押せない「タイムラインを作る」、「解析中の写真があと {N} 枚あります。終わると作れます。」 |
| 何も無い・解析中の写真が無い | 上と同じで「タイムラインを作る」が押せる。押すと `POST …/timeline` |
| 案を出している（下書きの `phase: "proposing"`） | 進み具合の印（回る輪）と「タイムラインの案を作っています」「ふつうは1分ほどで終わります。混んでいると10分ほどかかることがあります。この画面を閉じても続きます。」 |
| 確かめ待ち（`phase: "reviewing"`） | 「タイムラインの案ができました」「場面の分け方を確かめてから、AI が見出しと一言を書きます。」と「案を確認する」（§8.4 を開く） |
| 文を書いている（`phase: "writing"`） | 「見出しと一言を書いています」「ふつうは1分ほどで終わります。この画面を閉じても続きます。」と、3つの段（「タイムラインの案」「案の確認」「見出しと一言」）のどこまで済んだか（済んだ2つに印、書いている段に進み具合） |
| 失敗（`job.state: "failed"`） | 案なら「タイムラインの案を作れませんでした」と「もう一度」（`POST …/timeline`）。文なら「見出しと一言を書けませんでした」と「もう一度」（`POST …/draft/write`）・「案を確認する」 |

「やめる」は出さない。作り始めたら最後まで進む（2026-10-28 に人間が決定。要らなくなったら、できた後に作り直す。5-6。それまでは「やめる」と確認のダイアログ「作りかけのタイムラインを捨てますか？」→ `DELETE …/timeline/draft` があった）。
待ち時間の添え書きは、AI がすぐ終わると思わせないため（普段は数十秒で済むが、実行環境の入れ替えで処理が止まると、再投入のタイマーが拾うまで 10 分ほどかかる。2026-10-28 に本番で起きた。[06 §8.1](./06_processing_design.md#81-構成)）。
「タイムラインを作る」・「もう一度」は、受け付けた応答の `draft` で表示を進める（読み直さない）。

### 8.3 完成したタイムライン

**実装済み**（5-4a・5-4b。`widgets/timeline_current_view.dart`・`widgets/trip_timeline_view.dart`、サムネイルは `widgets/timeline_thumbnail.dart`、日付と時刻の表記は `utils/timeline_format.dart`、写真が変わった案内は `widgets/timeline_notices.dart`（5-4b））。
**実装済み**（5-5c）: 見出しの無い場面の「見出しなし」。残せなかった文の案内と「閉じる」を消した（アプリは応答の `droppedEdits` を読まない。API は応答の `droppedEdits` と `DELETE …/dropped-edits` を 5-5d で消した。[05 §5.15](./05_api_design.md#515-タイムライン段階5)）。
**実装済み**（5-6。メニューは `screens/trip_detail_screen.dart`・`widgets/trip_timeline_view.dart` の `TimelineMenu`、案内は `_buildEditBanner()`、作成日時は `widgets/timeline_current_view.dart`）: 「タイムラインを編集」「タイムラインを作り直す」を旅行詳細のメニューに移したこと、作成日時を一番下に出すこと、タイムラインを編集している途中の案内と「やめる」のダイアログの文言。
**実装済み**（T-2。`widgets/timeline_current_view.dart`、`models/timeline.dart` の `TimelineCurrent`）: 撮影日時の無い写真を出さないこと（「日時なし」の欄をなくし、応答の `undatedPhotos` を読まない。[02 §5](./02_design_overview.md#5-人間に決めてもらう点推奨付き) #54）。

- 旅行詳細の上のバーのメニュー（§8.1）に「タイムラインを編集」（`POST …/recut` → §8.4）・「タイムラインを作り直す」（§8.6）。タイムラインを編集している途中（下書きがある間）はこの2つを出さない。
  解析中の写真がある（`pendingPhotoCount > 0`）間は「タイムラインを作り直す」を押せない状態で出し、項目の下に小さく「解析中の写真があと {N} 枚」を添える（「タイムラインを編集」は解析中でも押せる）。操作を送っている間と、サムネイルから開く写真を読んでいる間はどちらも押せない（§8.1）。
  （5-6 より前は、完成版の上に「区切りを直す」「作り直す」のボタンと「解析中の写真があと {N} 枚あります」を置いていた。5-6 でメニューに移した）
- 一番下に小さく中央寄せで「{M}月{d}日 {H}:{mm} に作成」（`writtenAt` を端末の時刻で。時は 0 埋めしない。5-6 で一番上から移した）
- **タイムラインを編集している途中**（下書きの `reason: "recut"`）は、完成版を出したまま、その上に「タイムラインを編集している途中です」と「続ける」（§8.4）・「やめる」を出す。
  「やめる」は確認のダイアログ「編集をやめて、今のタイムラインのままにしますか？」と「キャンセル」「やめる」→ `DELETE …/timeline/draft` → `GET …/timeline` を読み直す（案の確認画面の「やめる」も同じダイアログ）。
  5-5a より前に文を書く段に進んだ区切りの直しの下書きは、書く待ち・書いている間（ワーカーが AI を使わずに当てる。[06 §8.3](./06_processing_design.md#83-文を書くstep-write)）は「見出しと一言を書き直しています」（操作は無い）、失敗したら「見出しと一言を書き直せませんでした」と「もう一度」・「案を確認する」・「やめる」で、「もう一度」は AI を使わずその場で完成版に当たって応答に下書きが無いので、タイムラインを読み直す（読み込み中にはせず、読めたら表示を替える。下書きの案内は消える。5-5a で実装済み）
- 作った後に写真が変わった（`changes.added + changes.removed > 0`）ら、案内「作った後に写真が {added} 枚増え、{removed} 枚消えました。今のタイムラインには入っていません。」と「あとで」「作り直す」（0 枚の側は書かない。増えただけなら「作った後に写真が {added} 枚増えました。…」、消えただけなら「作った後に写真が {removed} 枚消えました。…」。「あとで」はその表示の間（タイムラインを開き直すか読み直すまで）だけ隠す。下書きがある間は出さない）。案内の「作り直す」はメニューの「タイムラインを作り直す」と同じ（§8.6 の確認のダイアログを出す）で、解析中の写真がある間と操作を送っている間は押せない
- 案内は一番上に、写真が変わった案内を出し、その下に編集している途中の案内を置く
  （5-5c より前は、残せなかった文（応答の `droppedEdits`）があれば一番上に「場面や日が無くなったため、手で直した文のうち {N} 件を残せませんでした」とその文・「閉じる」（`DELETE …/dropped-edits`）を出していた。作り直しが前の文を使わなくなり（5-5b）、残せなかった文が無くなったので消した。API の側も 5-5d で消した）
- 日: 「{N}日目」「{M}月{d}日（{曜日}）」、タイトル、まとめ。どちらかを利用者が直していれば「編集済み」、どちらも AI なら「AI のまとめ」の印。右に編集のボタン（読み上げ「この日を編集」）
- 場面のカード: 見出しの印（食べ物の写真がある場面（`hasFood`）は橙、それ以外は青。色だけに頼らず見出しの文字で分かる）・時刻（1枚なら「7:50」、複数なら「10:10〜11:40」）・「地名 · 名前」・一言・サムネイル（4枚まで。それより多ければ「+{N}枚」）。右に編集のボタン（読み上げ「この場面を編集」）。
  1行目に印と見出し、2行目に「{時刻} · {地名} · {名前}」（地名・名前はそれぞれ「、」でつなぎ、無い側は省く）、3行目に一言、その下にサムネイル。5枚以上なら4枚の後に「+{残りの枚数}枚」を置く（押せない）
- 文が無い（`null`）日のタイトル・まとめ、場面の一言は、その行を出さない（日の印も、タイトルとまとめが両方無ければ出さない）。場面の見出しが無い（区切りを直して新しくできた場面）ときは、見出しの所に薄い字で「見出しなし」と出す（見出しの印は出さない。編集のボタンで書ける。5-5c で実装済み）
- サムネイルをタップすると、その写真を写真ビューアで開く（最初の版はその1枚だけ。`GET /api/photos/{photoId}` で読む）。写真を読んでいる間と操作を送っている間は、ほかのサムネイルのタップも操作のボタンも受け付けない（写真ビューアや確認画面を重ねて開かない）。写真が消えていたら（404 `PHOTO_NOT_FOUND`）「この写真は削除されています」をスナックバーに出してタイムラインを読み直し、それ以外の失敗はエラーの文言（`ApiException.userMessage`。それ以外は「写真の読み込みに失敗しました」）をスナックバーに出して表示はそのまま。写真ビューアを閉じたら、タイムラインを読み直す（ビューアで消した・直したことを出すため。読み込み中にはせず、読めたら表示を替える）。
  サムネイルの読み上げのラベルは撮影日時（§8.4 と同じ）
- 「タイムラインを編集」で受け付けたら、そのまま案の確認画面（§8.4）を開く。「続ける」「案を確認する」も §8.4 を開き、閉じたら §8.4 のとおり読み直す。操作の失敗は §8.1 と同じ
- 撮影日時の無い写真は出さない（タイムラインに入れない。2026-10-31 に人間が決定。[02 §5](./02_design_overview.md#5-人間に決めてもらう点推奨付き) #54。T-2 で実装済み。それまでは最後に「日時なし」として5列で並べ、タップで写真ビューアを開いていた。応答の `undatedPhotos` は読まない）
- 撮影時刻は写真の `takenAt` のまま出す（タイムゾーンを変換しない。写真の一覧と同じ）

### 8.4 案の確認画面（タイムラインを編集）

**実装済み**（5-3b。`screens/timeline_review_screen.dart`、確認のダイアログは `widgets/timeline_confirm_dialog.dart`）。
**実装済み**（5-5c）: 区切りの直し（`recut`）の説明の添え書き。
**実装済み**（5-6。`screens/timeline_review_screen.dart`、ダイアログは `widgets/timeline_confirm_dialog.dart` の `confirmTimelineAction()`・`confirmDiscardEdit()`）: 見出し・メニュー・下のボタンを作る・作り直すときと編集するときで分けたこと、読み込み中と失敗の既定の文言、区切りの保存の失敗の既定の文言。
**実装済み**（T-2。`screens/timeline_review_screen.dart` の `_showPhotoMenu()`・`_exclude()`）: 写真をタイムラインから外すこと（長押しのメニューの「タイムラインから外す」と確認のダイアログ。[02 §5](./02_design_overview.md#5-人間に決めてもらう点推奨付き) #52）と、撮影日時の無い写真を出さないこと（#54）。

作る・作り直すときの「タイムラインの案」の確認と、完成版の「タイムラインを編集」（区切りの直し。`reason: "recut"`）は同じ画面で、見出し・メニュー・下のボタンだけが違う（5-6 で文言を改めた）。

- 見出しは、作る・作り直すとき「タイムラインの案」、タイムラインを編集するとき「タイムラインを編集」（開く側の旅行詳細が、下書きの `reason` が `recut` かで決めて渡す。読み込み中と失敗の間も出す）。左上の「×」で旅行詳細に戻る（区切りは直すたびに保存しているので、続きから確かめられる）。`GET …/timeline/draft` の `days` を出す
- 上に説明「AI が写真を場面に区切りました。写真を長押しすると『ここで区切る』、場面の境目の『つなげる』で前の場面とまとめられます。」（タイムラインを編集するときは「写真を長押しすると…」から始め、その後に「新しくできた場面は見出しなしになります。つなげると、後ろの場面の見出しと一言は消えます。」を足す。足したのは 5-5c で実装済み）
- 日ごとに「{N}日目」「{M}月{d}日（{曜日}）」、その下に場面のカード。カードには時刻・地名・枚数と、場面の写真を5列のサムネイルで全部並べる
- 写真を長押しすると下からメニュー: 「この写真から新しい場面」（場面の最初の写真では出さない）と「タイムラインから外す」（どの写真にも出す。T-2）。同じ日の場面の間に「つなげる」を置く（日の境目には置かない）
- 「タイムラインから外す」は確認のダイアログ「タイムラインから外しますか？」「写真は旅行に残ります。外した写真は、タイムラインを作り直すまで戻せません。」と「キャンセル」「外す」（`confirmTimelineAction()`）。「外す」で `POST …/draft/excluded-photos`（その1枚の id）を送り、応答で描き直す（外した写真は出ず、写真を全部外した場面と日も出ない。場面の最初の写真を外しても場面のコメントは残り、場面の `startPhotoId` は外した写真の id のまま（区切りの保存の `sceneStarts` にもその id を送るので、その場面も「つなげる」などで直せる。「この写真から新しい場面」を出さない「場面の最初の写真」は、出している写真の最初）。[05 §5.15](./05_api_design.md#515-タイムライン段階5)）。「キャンセル」なら何も送らない。
  送っている間と失敗・重なりの扱いは区切りの保存と同じ（下の行。失敗の既定の文言は「タイムラインの操作に失敗しました」）。タイムラインを編集しているとき（`recut`）に外した写真は「保存」で完成版に入り、「やめる」と捨てる
- 操作ごとに `PUT …/draft/scenes` で保存し、応答で描き直す（応答が来るまで表示は変えない）。送る `sceneStarts` は、表示している場面の `startPhotoId` を撮影の順に並べ、「この写真から新しい場面」ならその写真の id をその場面の `startPhotoId` の次に足し、「つなげる」ならその場面の `startPhotoId` を外したもの。
  送っている間は他の操作（「つなげる」・写真の長押し・メニュー・下のボタン）を受け付けない（「×」と戻る操作は受け付ける）。失敗したら表示は直す前のまま、エラーの文言をスナックバーに出す
- 上のバーのメニューは、作る・作り直すとき「AI に案を出し直してもらう」だけ（確認のダイアログ「AI がもう一度案を出します。この画面で直した場面の分け方は消えます。」と「キャンセル」「出し直す」→ `POST …/timeline` → 旅行詳細に戻る）。
  タイムラインを編集するときは「やめる」だけ（§8.3 と同じダイアログ → `DELETE …/timeline/draft` → 旅行詳細に戻る）。
  （5-6 より前は、どちらにも「区切り案を出し直す」と「やめる」があり、完成版がある下書きの「区切り案を出し直す」は作り直しのダイアログだった。作り直しは旅行詳細のメニューからに絞り、作る途中の「やめる」はなくした）
- 下に「この案で見出しを付ける」と「{日数}日で {場面数} 場面 · 見出しと一言は AI が書きます」（日数は写真のある日の数）。押すと `POST …/draft/write` → 旅行詳細に戻る。
  タイムラインを編集するときは「保存」と「{日数}日で {場面数} 場面 · 見出しと一言はそのまま残します」で、押すと `POST …/draft/write`（AI を使わずその場で完成版に当てる。[05 §5.15](./05_api_design.md#515-タイムライン段階5)）→ 旅行詳細に戻り、タイムラインを読み直す（AI を待たずに直した完成版が出て、「タイムラインを編集している途中です」は消える。5-5a で実装済み）
- 撮影日時の無い写真は出さない（タイムラインに入れない。§8.3 と同じ。T-2 で実装済み。それまでは最後に「日時なし」として並べていた）
- 開くたびに `GET …/timeline/draft` を読む。読み込み中は「読み込み中...」、失敗は「エラーが発生しました」・エラーの文言（`ApiException.userMessage`。それ以外は「読み込みに失敗しました」）・「再試行」（押すと読み込み中に戻して読み直す）。読めるまでは上のバーのメニューと下のボタンを出さない。
  下書きが無い・確かめられる状態でない（確かめ待ちでも、文を書くのに失敗したのでもない）なら「タイムラインが変わりました。読み直しました」をスナックバーに出して旅行詳細に戻る。文を書くのに失敗した下書きも開け、区切りを直すと確かめ待ちに戻る（[05 §5.15](./05_api_design.md#515-タイムライン段階5)）
- 場面のカードの上に「{時刻} · {地名} · {N}枚」（時刻は §8.3 と同じ形で、撮影時刻をタイムゾーンを変換せずに出す。地名は場面の `placeNames` を「、」でつなぎ、無ければ省く）。写真の長押しで下から出るメニューに「この写真から新しい場面」と「タイムラインから外す」（上の行）。
  サムネイルの読み上げのラベルは撮影日時（写真のグリッドと同じ形。§3）
- 操作（区切りの保存・写真を外す・出し直す・やめる・見出しを付ける・保存）が 409 `TIMELINE_STATE_CONFLICT`・404 `TIMELINE_NOT_FOUND` を受けたら、「タイムラインが変わりました。読み直しました」をスナックバーに出して旅行詳細に戻る。
  404 `TRIP_NOT_FOUND`（読み込みでも）は旅行詳細に戻る（旅行詳細が「この旅行は削除されています」にする）。それ以外の失敗はエラーの文言（`ApiException.userMessage`。それ以外は、区切りの保存なら「保存に失敗しました」、ほかは「タイムラインの操作に失敗しました」）をスナックバーに出し、表示はそのまま
- 旅行詳細に戻ったら（「×」・戻る操作も）、旅行詳細の「タイムライン」は `GET …/timeline` を読み直す（読み込み中にはせず、読めたら表示を替える。失敗したら §8.1 の操作の後の読み直しと同じく、読み込みの失敗の表示）

### 8.5 編集シート

**実装済み**（5-4b。`widgets/timeline_edit_sheet.dart`。欄の下の添え書きの今の文言は 5-5c）。

- 場面: 見出し（30 文字まで）・一言（200 文字まで）。日: タイトル（40 文字まで）・まとめ（400 文字まで）。下から出るシートで、「キャンセル」「保存」。
  シートの見出しは「場面を編集」・「{N}日目を編集」、欄の名前は「見出し」「一言」・「タイトル」「まとめ」。今の文を入れて開く（文が無ければ空）。欄の文字数は上限で止める
- 「保存」で `PATCH …/scenes/{photoId}` / `PATCH …/days/{date}`。送るのは変えた欄だけ（前後の空白を除いて比べる。空にした欄は `null`）。何も変えずに保存したら送らずに閉じる（コメントの編集と同じ）。保存できたら閉じ、応答（`GET …/timeline` と同じ形）で描き直す
- 欄の下に、場面のシートは「空にすると、AI が書いた文に戻ります（AI が書いていない場面は空になります）」、日のシートは「空にすると、AI が書いた文に戻ります」（日は区切りを直しても足されないので、いつも AI の文がある。AI が書いていない場面（区切りを直して新しくできた場面）を空にすると空になる（5-5a で実装済み）が、アプリは場面に AI の文があるかを応答から知らないので、場面のシートでは両方を書く。5-5c で実装済み）
- シートは下に引いても閉じない（閉じるのは「キャンセル」とシートの外のタップ。保存中に引いて閉じると結果を受け取れないため）。保存している間は閉じられない（「キャンセル」「保存」も押せない。「保存」を続けて押しても送るのは1回）。失敗したらシートを開いたまま、エラーの文言（`ApiException.userMessage`。それ以外は「保存に失敗しました」）を出す。
  409 `TIMELINE_STATE_CONFLICT`・404 `TIMELINE_NOT_FOUND`（その日や場面が無くなった）なら閉じて「タイムラインが変わりました。読み直しました」を出して読み直す。404 `TRIP_NOT_FOUND` なら閉じて「この旅行は削除されています」（§8.1）
- 失敗してシートを開いたままのときは、欄の文は入力したまま残り、もう一度「保存」を押せる
- 日と場面の右の編集のボタンは、操作を送っている間と、サムネイルから開く写真を読んでいる間は押せない（§8.1・§8.3）
- タイムラインを編集している間も直せる。直した文は保存したときに残る（同じ場面なら）。作り直しを始めると完成版を出さないので、作り直しの間は直せない（5-6。API が完成版を消すのは 5-6b から。どちらも実装済み）

### 8.6 作り直す

**実装済み**（5-4a。`widgets/trip_timeline_view.dart`）。
**実装済み**（5-6。メニューは `screens/trip_detail_screen.dart`、ダイアログは `widgets/timeline_confirm_dialog.dart` の `confirmRebuildTimeline()`）: 旅行詳細のメニューから作り直すこと、確認のダイアログの文言、作り直すと今のタイムラインを出さずに §8.2 の表示になること。API が今のタイムラインを消すのは 5-6b で実装済み（`functions/timeline.ts` の `createTimeline`。5-6 のアプリを入れた後に出す）。

- 旅行詳細のメニューの「タイムラインを作り直す」と、写真が変わった案内の「作り直す」（§8.3）で、確認のダイアログ「タイムラインを作り直しますか？」「今のタイムラインを消して、今の写真で AI が最初から作り直します。手で直した文と場面の分け方も消え、元には戻せません。」と「キャンセル」「作り直す」（`widgets/timeline_confirm_dialog.dart` の `confirmRebuildTimeline()`。5-6 で文言を改めた）
- 「作り直す」で `POST …/timeline`（API が今のタイムラインを消して下書きを作る。5-6b で実装済み。[05 §5.15](./05_api_design.md#515-タイムライン段階5)）→ 今のタイムラインは出さずに §8.2 の「タイムラインの案を作っています」（受け付けた応答の `draft` で表示を進め、読み直さない。§8.2 の「タイムラインを作る」と同じ）。案の確認からもう一度進む。「キャンセル」なら何も送らず、表示もそのまま。操作の失敗（409 など）は §8.1 と同じ

### 8.7 場面のコメント

**実装済み**（5-7。`screens/timeline_review_screen.dart` の `_buildComment()`・`_editComment()`・`_merge()`、確認のダイアログは `widgets/timeline_confirm_dialog.dart` の `confirmMergeScenes()`）。2026-10-28 に人間が決定。

案の確認画面（§8.4）で、場面ごとに利用者がコメントを書ける。AI が見出しと一言を書くときの材料にする（そのまま見出しにはしない）。
AI は写真の名前と地名しか知らないので、「何をしていた場面か」を利用者が書くと、見出しと一言が当たりやすくなる。写真のコメント（写真ビューアの「コメントを編集」）とは別のもの。

- 場面のカードの写真の下に「＋ コメントを書く」（＋は印で、文字は「コメントを書く」）。押すと下から入力のシート（「場面のコメント」、100 文字まで、「キャンセル」「保存」）。
  書いたコメントはカードに「コメント: {コメント}」と出し、タップで直せる（今のコメントを入れてシートを開く。空・空白だけにして保存すると消え、「コメントを書く」に戻る）。「キャンセル」なら何も送らない。
  送っている間（§8.4）は「コメントを書く」もコメントのタップも受け付けない
- コメントは場面の最初の写真に付け、区切りと一緒に下書きに保存する（画面を閉じても、案の確認に戻れば残っている）。「AI に案を出し直してもらう」と、区切りと一緒に消える
- 『ここで区切る』で場面を分けると、前の場面がコメントを持ったままで、新しくできた場面は空
- 場面の最初の写真をタイムラインから外しても（§8.4）、コメントはその場面に残る（場面の id は外した写真の id のまま。T-2 で実装済み）
- 「つなげる」で場面をつなげると、前の場面のコメントを残す。前の場面に無く後ろの場面にあれば、後ろのコメントを引き継ぐ。
  **両方にあるときだけ**、確認のダイアログ「場面をつなげますか？」「前の場面のコメントを残します。後ろの場面のコメントは消えます。」と消えるコメント（「消えるコメント: {コメント}」）、「キャンセル」「つなげる」を出す（「キャンセル」なら何も送らない）
- タイムラインを編集するとき（`recut`）は AI を使わないので、コメントの欄を出さない。
  代わりに、つなげる後ろの場面に見出しか一言があるときは、同じ形の確認のダイアログ（「場面をつなげますか？」「つなげると、後ろの場面の見出しと一言は消えます。」と、消える文（見出しがあれば「消える見出し: {見出し}」、一言があれば「消える一言: {一言}」）、「キャンセル」「つなげる」）を出す（「キャンセル」なら何も送らない）。見出しも一言も無ければ確かめずにつなげる。
  見出しと一言は旅行詳細が読んだ完成版のもの（区切りの直しの下書きの応答には文が無い）
- 場面のコメントは、書く・直す・消すたびと、作る・作り直すときの「つなげる」で、区切りと一緒に送る（`PUT …/draft/scenes` の `sceneComments`。そのときの全部の場面のコメントを送る。[05 §5.15](./05_api_design.md#515-タイムライン段階5)）。
  『ここで区切る』と、タイムラインを編集するときの「つなげる」は `sceneComments` を送らない（サーバが残る区切りのコメントを残す）。コメントのシートは「保存」でシートの中から送り（編集シート §8.5 と同じく、保存している間は閉じられない。変えずに保存したら送らずに閉じる）、失敗したらシートと書いた文を残してエラーの文言（`ApiException.userMessage`。それ以外は「保存に失敗しました」）をシートの中に出す。下書きが変わった・旅行が無いときは、シートを閉じて区切りの保存と同じに扱う（§8.4）。区切りとつなげるときの保存の失敗・重なりの扱いは区切りの保存と同じ

## 9. アプリの作り（Flutter）

画面に共通する作りの方針と、API の失敗の見せ方（以前の `docs/05_technology_selection.md` §4.2・`docs/07_api_workflow.md` §2 から移した。2026-10-25）。

### 9.1 構成の方針

状態管理は `setState` で、`ApiService` などは画面のコンストラクタで渡す。画面遷移は `Navigator.push` / `pop`（`MaterialPageRoute`）で、名前付きルートは使わない。
状態管理ライブラリ（`provider` など）やルーティングライブラリ（`go_router` など）は導入していない。

この構成にしている理由（2026-10-11 に人間が決定。実態に合わせた）:

| 項目 | 方針 | 理由 |
|---|---|---|
| 状態管理 | `setState`。`ApiService` などは画面のコンストラクタで渡す | 画面をまたいで共有するクライアント状態が無く、扱うのはサーバのデータだけ（送信の列は `AppRoot` が持ち、画面に渡す。§4.7） |
| 画面遷移 | `Navigator.push` / `pop`（`MaterialPageRoute`）。名前付きルートは使わない | ディープリンクや Web の履歴に対応する予定が無い（Android のみ） |
| HTTP | `http`。テストは同梱の `MockClient` で差し替える | テストがこれに依存している |

**見直す条件**: 画面をまたいで共有するクライアント状態（お気に入り、絞り込み条件、オフラインのキャッシュなど）が要る機能を足すとき。
そのときは状態管理の方式を選び直し、**全画面を一度に移す**（`setState` と混在させると状態の所在が追えなくなる）。
`pubspec.yaml` には使うパッケージだけを宣言する。かつて `provider` / `go_router` / `dio` / `uuid` / `intl` が
使われないまま宣言されており、どれを使うべきか判断がぶれていた。

- 設定の保存: API キーは `flutter_secure_storage`、エンドポイントは `shared_preferences`
- 通信: `http`（multipart の Content-Type の指定に `http_parser` も使う）。Function Key はヘッダ `x-functions-key` で送る（`ApiService._headers`。写真の送信の multipart も同じヘッダを足す）。URL には載せない（[05 §9.1](./05_api_design.md#91-認証と宛先)）。
  ネットワーク状態の監視（`connectivity_plus`）は入れていない。通信の失敗は `ApiService._handleError()` が例外から見分ける
- 端末の文字サイズ設定は反映しない（倍率 1.0 に固定。`main.dart`）
- 言語の設定は日本語（ja_JP）だけ（`main.dart` の `supportedLocales`。Material の文言は `flutter_localizations`）。端末の言語が英語でも、文字を描く部品に日本語が渡るので、端末では日本語の字形を選ぶ
  （設定が無いと英語として動き、英語の設定の端末では中国語の字形になりうる）。
  Web 版は、Flutter が漢字・かなの補いのフォントをブラウザの言語の設定で選ぶので、アプリの設定では変わらない（Flutter 3.32.8 で確かめた）。
  2026-10-26 に Web 版で「ヰ」などの字形が日本語のものでなかったが、Web 版は確認用なので直していない（実装済み。日本語の設定の作業単位）

### 9.2 エラー表示（`ApiException.userMessage`）

非 2xx の応答は `ApiException.fromResponse()` が例外にする。ボディをサーバの封筒
（`{ success: false, error: { code, message } }`。[05 §9](./05_api_design.md#9-共通の決まり)）として読めれば、`error.code` / `error.message` を
`ApiException` の `code` / `message` に入れる。封筒として読めないボディ（Azure Functions
ランタイムが返す 401、従量課金プランの過負荷時に返る 429 "Too Busy" など）では `code` は null、
`message` はステータス付きの固定文言「サーバーでエラーが発生しました（ステータス: {ステータス}）」になる。
それ以外の例外（通信例外や 2xx 応答の解析失敗など）は、`_handleError()` が
ステータス 0 の `ApiException` にする。通信の例外（`SocketException` と、`http` の `IOClient` が接続できない・途中で切れた例外を包む
`ClientException(message, uri)`）の `message` は固定文言「ネットワークに接続できません」。
例外の文言には宛先の URL が入りうるが、関数キーは URL に載せずヘッダで送るので、文言にキーは入らない（§9.1。2026-10-27。実装済み）。
関数キーにヘッダで送れない文字（見える ASCII 以外。全角文字や改行）があれば、要求を送らずにステータス 401 の `ApiException`（`userMessage` は「APIキーが無効です。設定を確認してください。」）にする。
そのまま送ろうとすると `http` が送る前に例外を投げ、その文言にキーがそのまま入るため（2026-10-27。実装済み）。

画面に出す文言は `ApiException.userMessage` がステータスから決める。

| ステータス | 表示文言 |
|---|---|
| 0 | ネットワークに接続できません。インターネット接続を確認してください。 |
| 401 | APIキーが無効です。設定を確認してください。 |
| 404 | 要求されたデータが見つかりません。 |
| 429 | サーバーが混雑しています。しばらく待ってから再試行してください。 |
| 500 | サーバーで問題が発生しています。しばらく待ってから再試行してください。 |
| 502 | 外部サービスでエラーが発生しました。繰り返し発生する場合は、時間を置いてからお試しください。 |
| 503 | サービスに一時的に接続できません。しばらく待ってから再試行してください。 |
| それ以外（400・409・413・415 など） | `message`（サーバの `error.message`。封筒を読めなければ上記の固定文言） |

同じステータスでも `code` で意味が違うものがある（404 は `TRIP_NOT_FOUND`・`PHOTO_NOT_FOUND` と宛先の誤り）。画面の分岐はステータスではなく `code` で行う（例: `ApiException.isTripNotFound`）。
401 を検知して自動で設定画面へ移ることはしない（文言を出すだけ）。

### 9.3 写真の送信の Content-Type（クライアント）

写真の送信（`POST /api/photos`）で、アプリは `image` パートの Content-Type を、拡張子や OS の申告値ではなく
ファイル先頭のシグネチャから決める（`mobile/lib/utils/image_mime_type.dart`）。

| 形式 | 先頭のバイト列 | 送る Content-Type |
|------|---------------|------------------|
| PNG | `89 50 4E 47 0D 0A 1A 0A` | `image/png` |
| JPEG | `FF D8 FF` | `image/jpeg` |
| GIF | `GIF87a` または `GIF89a`（ASCII） | `image/gif` |
| WebP | 先頭が `RIFF`、8バイト目から `WEBP`（ASCII） | `image/webp` |

サーバは送られた Content-Type を許可する形式と照合するだけで中身は見ず、そこから Blob の Content-Type と拡張子を決める。
そのため拡張子が `.jpg` でも中身が PNG なら `image/png` で送る。
どのシグネチャにも当たらない中身は `image/jpeg` として送る。HEIC など4形式以外もこの既定値のまま受理される
（扱いは `docs/09_backlog.md` の「判定できない画像形式を `image/jpeg` として送る」で判断待ち）。
