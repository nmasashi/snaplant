# 提案（未トリアージ）

`improvement-scout` サブエージェントがリポジトリを読んで出した提案を置く場所。

## この文書の位置づけ

**ここに書かれているものは、まだやると決まっていない。**

| 文書 | 内容 | 誰が書くか |
|---|---|---|
| [バックログ](./09_backlog.md) | **検証済みで実在する**課題・未実装機能 | 人間、または根拠を確認したエージェント |
| この文書 | **トリアージ待ちの提案** | `improvement-scout` |

採用すると決めた項目は、**人間がバックログへ移動**する。
エージェントはこの文書にだけ書き込み、バックログには触れない。
バックログの「すべての項目が検証済み」という性質を保つため。

却下した提案は、**理由を添えて「却下」節へ移す**。消さないこと。
同じ提案が繰り返し出てくるのを防ぎ、なぜ却下したのかを残すため。

## 確度の階層

提案には必ず階層を付ける。**階層が低いほど根拠が弱い。**

| 階層 | 内容 | 根拠 |
|---|---|---|
| **1** | 実装済みだが到達不能・未活用 | コードそのもの |
| **2** | 文書化された意図が未実現 | 設計文書・要件定義 |
| **3** | 運用上の弱点（コスト・監視・障害時の挙動） | コードと構成から読める |
| **4** | 純粋な新機能・改善アイデア | 推測を含む |

## 記載フォーマット

各提案は次の項目を必ず埋める。**根拠を引用できない提案は書かない。**

```markdown
### [階層N] タイトル

**根拠**: `path/to/file.ext:行番号` — 何がそこに書かれているか

**現状**: 今どうなっているか（事実のみ）

**提案**: 何をするか

**メリット**: 誰にとって何が良くなるか。可能なら定量的に

**デメリット・コスト**: 工数感、新たに増える依存・保守対象、ランニングコスト

**リスク**: 失敗した場合・想定どおりにならなかった場合に何が起きるか

**影響範囲**: どのレイヤー・ファイル群に触るか

**代替案**: 他の実現方法があれば。「何もしない」も選択肢として評価する

**やらない場合**: 放置したときに何が起きるか。何も起きないならそう書く

**判断に必要な情報**: エージェントには分からず人間が持っている前提
（利用規模、予算、今後の方針など）。不要なら「なし」
```

## 却下

### Cosmos の SQL を検証する層を作る

**却下理由: 環境が1つしかないため E2E が成立しない。**
本番に対してテストデータを作って消すことになり、実データと混ざるリスクがある。
Cosmos DB Emulator は Linux コンテナ版があるが、起動に時間がかかり CI の
フィードバックを遅くする。単体テストの速さを守る方が原則1（迅速なフィードバック）に沿う。

**代替として採用したもの**: CLAUDE.md に「Cosmos のクエリを変更したら手で確認する項目」を
常設の手順として置いた。バックログは対応後に項目を削除する運用なので常設には向かない。

以下は却下した案の記録（同じ提案の蒸し返しを防ぐため）。

絞り込み（`WHERE`）・並び順（`ORDER BY`）・射影（`SELECT` の列）の正しさを
検証しているテストは実質存在しない。単体テストの偽物は SQL 文字列を解釈しないため
原理的に検証できない。実測した穴（変異を入れて全スイートを実行した結果）:

- `getPlantByName`（現在は削除済み）の `WHERE c.name = @name` を削除 → **全スイートで未検出**
- `getPlants` の射影を `SELECT *` に変更 → **全スイートで未検出**。
  これは `GET /api/plants` のレスポンスに `description` / `updatedAt` / `scientificName`
  まで漏れる退行で、OpenAPI の `PlantSummary` 契約に直接当たる

`.claude/test-principles.md` の原則2は「エミュレータ未導入のため SDK モックを許容する。
この妥協を埋め合わせるのは E2E テストの役割」と定めているが、**その E2E が存在しない**。

案は `deploy-functions.yml` の後段にデプロイ後の実リソースに対する契約テストを足すもので、
最小限、次の3つを見れば空いている穴は埋まる（これが手で確認する項目になった）。

- `GET /api/plants` のレスポンスに `description` / `updatedAt` /
  `scientificName` が**含まれない**こと（射影が効いている）
- `GET /api/plants` が `createdAt` の降順であること
- `GET /api/plants/check-duplicate` が別名の植物を拾わないこと

実データを作って消す必要があるため、本番とは別のテスト用コンテナか、
テスト用 ID の接頭辞で後片付けする仕組みが要る。ここが設計のポイントだった。
