## この文書の位置づけ

**ここに書かれているものは、まだやると決まっていない。**

| 文書 | 内容 | 誰が書くか |
|---|---|---|
| [バックログ](./09_backlog.md) | **検証済みで実在する**課題・未実装機能 | 人間、または根拠を確認したエージェント |
| この文書 | **トリアージ待ちの提案** | `improvement-scout` |

採用すると決めた項目は、**人間がバックログへ移動**する。
エージェントはこの文書にだけ書き込み、バックログには触れない。
バックログの「すべての項目が検証済み」という性質を保つため。

却下した提案は、**理由を添えて「却下」節へ移す**。消さないこと。
同じ提案が繰り返し出てくるのを防ぎ、なぜ却下したのかを残すため。

## 確度の階層

提案には必ず階層を付ける。**階層が低いほど根拠が弱い。**

| 階層 | 内容 | 根拠 |
|---|---|---|
| **1** | 実装済みだが到達不能・未活用 | コードそのもの |
| **2** | 文書化された意図が未実現 | 設計文書・要件定義 |
| **3** | 運用上の弱点（コスト・監視・障害時の挙動） | コードと構成から読める |
| **4** | 純粋な新機能・改善アイデア | 推測を含む |

## 記載フォーマット

各提案は次の項目を必ず埋める。**根拠を引用できない提案は書かない。**

```markdown
### [階層N] タイトル

**根拠**: `path/to/file.ext:行番号` — 何がそこに書かれているか

**現状**: 今どうなっているか（事実のみ）

**提案**: 何をするか

**メリット**: 誰にとって何が良くなるか。可能なら定量的に

**デメリット・コスト**: 工数感、新たに増える依存・保守対象、ランニングコスト

**リスク**: 失敗した場合・想定どおりにならなかった場合に何が起きるか

**影響範囲**: どのレイヤー・ファイル群に触るか

**代替案**: 他の実現方法があれば。「何もしない」も選択肢として評価する

**やらない場合**: 放置したときに何が起きるか。何も起きないならそう書く

**判断に必要な情報**: エージェントには分からず人間が持っている前提
（利用規模、予算、今後の方針など）。不要なら「なし」
```

## 提案

### [階層1] Flutter 側のアーキテクチャ方針を決め、未使用パッケージを整理する

**根拠**: `mobile/pubspec.yaml` に宣言されているが、`mobile/lib` 配下で
`package:` インポートが 0 件のパッケージが5つある。

| パッケージ | 宣言された用途 | 使用ファイル数 |
|---|---|---|
| `provider` | 状態管理 | 0 |
| `go_router` | ルーティング | 0 |
| `dio` | HTTP クライアント | 0 |
| `uuid` | ID 生成 | 0 |
| `intl` | 国際化・日付整形 | 0 |

**現状**: 実態は宣言と食い違っている。

- 状態管理は `setState` のみ（`mobile/lib` 配下で `setState` / `StatefulWidget` が計37箇所）
- HTTP は `http` パッケージ（`mobile/lib/services/api_service.dart`）
- ルーティングは `mobile/lib/main.dart` の `onGenerateRoute` で手書き。
  ただし `switch` の `default` が常に初期画面を返すだけで、実質機能していない
- ID 生成はサーバ側（`api/src/services/cosmosService.ts`）が担当しているため
  クライアントでは不要
- 日付整形は `mobile/lib/models/plant.dart` が `DateTime.parse` /
  `toIso8601String` で自前処理

**提案**: 2段階で進める。

1. **アーキテクチャ方針を決めて CLAUDE.md に記録する** —
   状態管理・ルーティング・HTTP クライアントのそれぞれについて、
   現状維持か移行かを決める
2. **決定に合わせて `pubspec.yaml` を整理する** — 使わないものを削除する

**メリット**:

- **判断のゆれが止まる。** 現状では次に画面を追加する人が
  `setState` を続けるか `provider` を使い始めるか判断できない。
  混在すると状態の所在が追えなくなる
- 依存が減り、`flutter pub get` の解決対象と脆弱性の監視対象が減る
- `pubspec.yaml` が実態を表すようになり、新規参加者の誤解がなくなる

**デメリット・コスト**:

- 方針決定そのものに設計判断が必要（下記「判断に必要な情報」参照）
- `provider` 等を**採用する**方針にした場合は、既存5画面の
  状態管理を書き換える工数が発生する（37箇所の `setState` が対象）
- 現状維持＋削除なら、`pubspec.yaml` の編集と `flutter pub get` のみで済む

**リスク**:

- 削除したパッケージを後で使いたくなった場合、再追加は容易なので低リスク
- 一方で `provider` 導入を選ぶと、途中まで移行した中途半端な状態が
  最も危険（`setState` と `provider` の混在）。やるなら一度に完了させる

**影響範囲**:

- 現状維持＋削除: `mobile/pubspec.yaml`, `mobile/pubspec.lock`
- `provider` 導入: 上記に加えて `mobile/lib/screens/` 配下の全5画面

**代替案**:

- **何もしない** — 未使用依存が残るが実行時の害はない。
  ただし判断のゆれは解消されないため、画面を追加するたびに同じ問題が再発する
- **方針だけ決めて pubspec は触らない** — 判断のゆれは止まる。
  依存の掃除は後回しにできる。最小コストで主要なメリットが得られる

**やらない場合**: 実行時の不具合は起きない。ただし画面追加のたびに
状態管理の方式を都度判断することになり、実装者によって方式が混在する。
混在が進むほど後からの統一コストが上がる。

**判断に必要な情報**:

- **今後どこまで画面・状態が複雑になる見込みか。** 現状の5画面・
  サーバ状態のみという規模なら `setState` で十分。画面間で共有する
  クライアント状態（お気に入り、フィルタ条件、オフラインキャッシュなど）が
  増える見込みなら `provider` 等の導入に意味がある
- **ディープリンクやブラウザ履歴対応の予定があるか。**
  あれば `go_router` に実益がある。なければ手書きで足りる
- **多言語対応の予定があるか。** あれば `intl` を残す
