## 1. 目的

旅行中に撮った写真をアップロードして、旅行ごとのアルバムとして見られるようにする。
写真は AI が大きなカテゴリに分け、風景・食べ物・植物は名前まで識別して、種類ごとの図鑑にまとめる。

今の SnapPlant（植物の写真を1枚ずつ識別して図鑑に登録するアプリ）を土台に広げる。

## 2. 前提

- **利用者は本人だけ**（当面）。共有やログインは使う人が決まってから考える
- **端末は Android**。旅行で使う端末は SC-03K（Android 10）
- **個人利用なので、費用を抑える。** 環境は本番の1つだけ
- **既存機能が壊れることは、ある程度許容する。** 既存の機能や考え方は、流用できるものを積極的に使う
- 規模は1回の旅行で数百枚を想定する

## 3. 用語

| 用語 | 意味 |
|---|---|
| 旅行 | 写真をまとめる単位。名前を付ける（例: 「北海道 2026秋」） |
| 写真 | アップロードした1枚。ふつうは1つの旅行に属するが、**どの旅行にも属さない写真もある** |
| タグ | 写真や旅行に付ける目印。AI が付けるカテゴリのほか、お気に入りなど利用者が付けるものもある |
| カテゴリ | AI が写真に付ける大きな分類（風景・食べ物・植物・その他など）。タグの一種として付く |
| 識別 | カテゴリが風景・食べ物・植物の写真について、AI が名前などを答えること |
| 図鑑 | 識別した結果を種類ごとにまとめたもの。1つの項目（例: 「サクラ」）に写真が複数ぶら下がる |
| タイムライン | 旅行の写真を、日ごと・場面ごとに撮影の順でまとめたもの。日にはタイトルとまとめ、場面には見出し（朝ごはん・食べ歩き など）と一言が付く |
| 場面 | タイムラインの中の、続けて撮った写真のまとまり（例: 昼ごはん、運河の散策）。撮影の順の写真の列に「区切り」を入れて分ける |

## 4. 段階

規模が大きいので、段階ごとに区切って1つずつ機能を広げる。

| 段階 | 内容 |
|---|---|
| 0. 片付け | Flutter の不具合の修正、`flutter analyze` の解消と CI |
| 1. 実機で確かめる | 写真から撮影日時と位置情報を読めるか |
| 2. 旅行アルバム（AI なし） | 旅行を作り、複数枚をまとめて送る。撮影日時と位置情報を保存し、日時順に並べる。画像は非公開 |
| 3. 大分類 | 送った写真を安価な LLM でカテゴリに分け、タグとして付ける。旅行の写真をカテゴリで絞り込める（旅行をまたいで種類ごとに見るのは段階4の図鑑） |
| 4. 詳しい識別と図鑑 | カテゴリに応じて識別に回し、種類ごとの図鑑にまとめる。今の植物図鑑をこの形に統合する |
| 5. タイムライン | 写真を送り終えた旅行から、日ごと・場面ごとにまとめたタイムラインを作る。AI が場面の区切りの案を出し、利用者が確かめてから、AI が見出しと一言を書く。文と区切りは後から直せる |
| 6. 旅行の自動まとめ | 撮影日時と位置情報から、旅行の区切りを提案する |
| 7. 自動アップロード | 新しく撮った写真を見つけて、裏で送る |
| （未定） | 共有・ログイン |

## 5. 機能要件

### 5.1 旅行

- 旅行を作れる。名前を付けられ、あとから変えられる【段階2】
- 旅行の一覧を見られる。各旅行の写真の枚数と、撮影の期間（最初と最後の撮影日時）が分かる【段階2】
- 旅行を削除できる。消す前に、中の写真も一緒に消すかを利用者に聞く（枚数を示す）。消さない場合、写真はどの旅行にも属さない写真として残る【段階2】
- 旅行の一覧は、新しい旅行が上に来る【段階2】
- **旅行にもタグを付けられる構造にする**（お気に入りなど）。タグの機能自体は後の段階で入れるが、
  後から足すときにデータの移し替えが要らないようにしておく【構造は段階2、機能は未定】

### 5.1.1 旅行に属さない写真

- **写真は、どの旅行にも属さなくてよい。** 旅行を決めずに送った写真や、旅行と関係のない写真を扱えるようにする【段階2】
- 旅行に属さない写真の一覧を見られる【段階2】
- 写真を**複数まとめて選んで**旅行に入れられる。旅行から外す（どの旅行にも属さない写真に戻す）こともできる【段階2】

### 5.2 写真の取り込み

- **あとでまとめて選んで送る。** 端末のギャラリーから複数枚を一度に選んで、一斉に送る。送り方は次の3つ【段階2】
  1. **旅行を選んでから送る**: 送り先の旅行を先に選び、選んだ写真をまとめてその旅行に送る
  2. **旅行を選ばずに送る**: どの旅行にも属さない写真として送る
  3. **送った後で旅行に割り当てる**: 2 で送った写真（どの旅行にも属さない写真）を、あとから複数まとめて選んで旅行に入れる
- 送信の進み具合（何枚中何枚か）が分かる。送信中にほかの画面へ移っても、送信は続く【段階2】
- 送れなかった写真は、失敗したことが分かり、送り直せる。通信が一時的に失敗したときは自動で何回か送り直す【段階2】
- **同じ写真を2回送っても、1枚として扱う。** 送り直しや選び直しで重複しない【段階2】
- 撮影日時と位置情報は、写真の付加情報（EXIF）から取る【段階2】
  - **位置情報は必須にしない。** 位置情報が無い写真も、すべての機能で扱える。位置情報は、あれば AI の解析の手がかりに使う程度
  - 撮影日時が無い写真も扱える（撮影日時順に並べるときは末尾に置くなど）
  - 写真にはタイムゾーンが記録されないので、撮影日時は「撮影した土地での時刻」として扱う
- 取り込みに AI を使わない。送った写真はすべてアルバムに残る（植物でない写真を拒んだりしない）【段階2】
- 裏での自動送信は最後の段階で入れる【段階7】

### 5.3 閲覧

- 旅行の写真を、撮影日時の順に一覧で見られる【段階2】
- 写真を1枚ずつ大きく見られる。撮影日時が分かる【段階2】
- **位置情報がある写真は、緯度・経度を地名（市区町村など）に変換して表示する。** 地名は識別の手がかりにも使える【段階は設計で決める】
- 写真を削除できる【段階2】
- 数百枚の旅行でも、一覧の表示が重くなりすぎない（小さな画像を使うなど）【段階2】

### 5.3.1 タイムライン

旅行を終えて写真を送り終えた後に、その旅行の写真から「1日目 朝ごはん 7:50 海鮮丼」のようなタイムラインを作る（2026-10-24〜25 に人間と決めた。決定は [02 §5](./02_design_overview.md#5-人間に決めてもらう点推奨付き) #41〜#48）。

- 旅行の写真から、日ごと・場面ごとにまとめたタイムラインを作れる。利用者が「タイムラインを作る」を押したときに作り、写真が増えるたびに自動では作らない【段階5】
- 作るのは2段。AI が場面の区切りの案を出し、利用者が確かめて直してから（写真から新しい場面にする・前の場面とつなげる）、AI が場面の見出しと一言、日のタイトルとまとめを書く【段階5】
- 区切りを確かめている途中でやめても、案と直したところは残り、続きから確かめられる。案を出し直すこともできる【段階5】
- 解析（分類・識別）が済んでいない写真があるうちは作れない（料理の名前などが無いと見出しが書けないため）。解析に失敗した写真（分類・識別とも）と、解析の対象でない写真（段階2に送った写真）は済んだものとして扱う【段階5】
- 日は撮影日時で分け、旅行で一番早い写真の日を1日目とする。日付の切り替えは朝4時（深夜に撮った写真は前の日に入る。時刻はサーバの設定で変えられる）。撮影日時の無い写真は最後に「日時なし」としてまとめる【段階5】
- AI に渡すのは、写真の撮影時刻・カテゴリ・名前・地名・コメントの文字だけで、写真そのものは渡さない（費用を抑える。要件 6 の「費用」）【段階5】
- 完成した後も、日のタイトルとまとめ、場面の見出しと一言を手で直せる。区切りも直せる。区切りを直しても AI は使わず、新しくできた場面の見出しと一言は空（利用者が書く）、つなげた場面は前の場面の見出しと一言が残る（2026-10-27 に変更）【段階5】
- いつでも作り直せる。作り直しは AI が区切りの案から一から作り、手で直した文と区切りは消える（作る前に知らせる。2026-10-27 に変更）。AI が動くのは、作るときと作り直すときだけ。作った後に写真が増えた・消えたときは、そのことを知らせる（増えた写真をタイムラインに入れるには作り直す）【段階5】
- 作り直し・区切りの直しの途中も、完成したタイムラインを見られる。途中でやめると、完成したタイムラインのまま残る【段階5】
- 最初の版では、写真を別の場面へ移す（区切り以外で場面の中身を変える）こと、地図、共有は入れない

### 5.4 大分類とタグ

- 送った写真を、AI がカテゴリ（風景・食べ物・植物・その他など）に分ける。分類は裏で行い、送信を待たせない【段階3】
- 分類には、識別とは別の**安価な LLM** を使う。モデルは差し替えられるようにする【段階3】
- カテゴリはタグとして写真に付く。旅行をまたいで種類ごとに見るのは図鑑（§5.5）で、旅行の中ではカテゴリで絞り込める【段階3・4】（段階3で入れたカテゴリ横断の画面は、図鑑と役割が重なるので 2026-10-24 に消した）
- 旅行の写真一覧を、カテゴリ（植物・食べ物・風景など）で簡単に絞り込める【段階3】
- **写真にも旅行にも、新しいタグを後から足せる構造にする**（AI のカテゴリ以外に、お気に入りなど利用者が付けるタグ）【構造は段階2】
- 分類の進み具合と、失敗した写真が分かり、失敗した写真はやり直せる【段階3】

### 5.5 識別と図鑑

- カテゴリが風景・食べ物・植物の写真だけを、詳しい識別に回す【段階4】
- **名前は AI が確定する。** 利用者が候補から選ぶ手間は無くす【段階4】
- 確証がないことが分かるよう、**信頼度**を持たせる。信頼度は0〜100【段階4】
- **名前はできるだけ細かい粒度で答えさせる。** 今の植物の識別の決まり（品種名が分かれば品種名、分からなければ種名、
  それも分からなければ属名）を流用し、食べ物・風景にも同じ考え方の決まりを作る【段階4】
- 他の候補（第2候補以降）は、データとしては残さない。AI が必要と判断したときに、一言コメントの中で
  「〇〇の可能性もある」のように補足する程度にする【段階4】
- **図鑑は、種類ごとの1件に、その種類が写った写真が複数ぶら下がる形**にする。植物・食べ物・風景のどれも同じ形【段階4】
  - 例: 図鑑の「サクラ」の項目に、旅行をまたいで撮ったサクラの写真がすべて並ぶ
  - 同じ種類（植物・食べ物・風景）で同じ名前のものは、1件にまとめる（当面は名前の完全一致）
- 図鑑の項目に持たせる情報【段階4】

  | 種類 | 共通の項目 | 種類ごとの項目 |
  |---|---|---|
  | 植物 | 名前・説明・特徴（一言コメント）・信頼度 | 学名・科名 |
  | 食べ物 | 同上 | 料理のジャンル（和食・中華など）・主な食材 |
  | 風景 | 同上 | 場所の種類（山・海・寺社・街並みなど）・場所の名前・地域 |

- **項目も種類も、後から増やせる構造にする。** 項目や種類を足すたびに、既存のデータの移し替えや、アプリの作り直しが要らないようにする【段階4】
- 撮影日時と位置情報（地名）があれば、識別の手がかりとして AI に渡す（特に風景）【段階4】

### 5.5.1 利用者による修正と、AI へのやり直しの依頼

- **写真のコメント（AI が付けた一言コメント）は、利用者が直せる**【段階4】
- **写真を指定して、AI に解析をやり直させられる。** カテゴリ（種類）の分類も、図鑑の項目の識別も対象【段階4】
  - やり直しを頼むときに、利用者がコメント（手がかり）を入れられる。AI はそれを手がかりにして解析する
    （例: 「これはサクラではなくウメ」「旭川のラーメン屋で食べた」）
  - 今の植物の識別にある「補足情報（`contextInfo`）を AI に渡す」仕組みを流用する

### 5.6 旅行の自動まとめ

- 撮影日時と位置情報から、旅行の区切りを提案する。写真を別の旅行へ移せる【段階6】

### 5.7 自動アップロード

- 新しく撮った写真をアプリが見つけて、裏で送る【段階7】
- 送信待ちの写真は、アプリを終了しても失われない【段階7】

### 5.8 今の植物図鑑の扱い

- 段階2・3では、今の植物図鑑はそのまま残し、アルバムとは別に動かす【段階2・3】
- **段階4で、植物図鑑をアルバムの図鑑（種類 = 植物）に統合する。** 今の植物の記録は新しい形へ移し、古い仕組み（植物1枚ずつの取り込みなど）は廃止する【段階4】

## 6. 非機能要件

| 項目 | 要件 |
|---|---|
| 公開範囲 | **アルバムの画像は最初から非公開にする。** 旅行の写真には人や場所が写るため。後で共有を足すときの作り直しも減る |
| 費用 | AI の費用を抑える。安価な LLM で分類してから、必要な写真だけを詳しく識別する。費用は実測して見積もる |
| 端末 | Android。旅行で使う端末は SC-03K（Android 10） |
| 位置情報 | 必須にしない（5.2） |
| 拡張性 | 図鑑の項目と種類を後から増やせる（5.5） |
| 既存の流用 | 今のレスポンスの形、エラーの扱い、認証（Function Key）、テストの仕組みなどは、流用できるものを使う |

## 7. 対象外・未定

- **共有・ログイン**: 使う人が決まるまで未定。画像を最初から非公開にしておくことで、後で足しやすくする
- **カメラでの撮影**: アプリから撮影する機能は今のところ入れない（端末のカメラで撮った写真を後で選ぶ）
- **iOS・Web**: 対象外

## 8. 未決の論点

| 論点 | 今の考え |
|---|---|
| 名前の揺れ（「ソメイヨシノ」と「サクラ」など）をどうまとめるか | 当面は名前の完全一致。名前の粒度はプロンプトの決まりで揃える（5.5）。それでも気になったら揃える機能を後で足す |
| 名前を利用者が直接書き換えられるようにするか | AI へのやり直しの依頼（5.5.1）で直すのが基本。直接書き換える機能は必要になったら |
| 地名への変換をどの段階で入れるか、何を使うか | 変換には外部の地図サービス（Azure Maps など）が要り、費用がかかりうる。段階と方法は設計で決める |

決まった論点（記録として残す）:

- AI が出した第2候補以降は、データとしては残さない。一言コメントの補足に留める（5.5）
- 旅行一覧は新しい旅行が上。旅行にもタグを付けられる構造にしておく（5.1）
