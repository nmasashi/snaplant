# テストの原則

このリポジトリのテストは Vladimir Khorikov『単体テストの考え方/使い方』に沿って書く。
いわゆる**古典学派（デトロイト学派）**の立場を取る。

`test-writer` と `test-reviewer` の両エージェントがこのファイルを唯一の基準として参照する。
執筆基準とレビュー基準は常に同一でなければならないため、原則をエージェント定義側に複製しない。

このファイルには**原則だけ**を書く。テストランナーの種類、ディレクトリ構成、
実行コマンド、依存の具体名といったプロジェクト固有の事実は CLAUDE.md 側にあり、
変わる可能性があるのでここには複製しない。

---

## 1. 良い単体テストの4本の柱

テストを書く・直す判断は、最終的にこの4つのトレードオフに還元される。

| 柱 | 意味 |
|---|---|
| **退行に対する保護** | バグが混入しそうになったときに検出できること |
| **リファクタリングへの耐性** | 振る舞いを変えない変更でテストが落ちないこと |
| **迅速なフィードバック** | すぐ気軽に実行できること |
| **保守のしやすさ** | テストコードが読みやすく、壊れた理由がすぐ分かること |

**このリポジトリでは「リファクタリングへの耐性」を最優先する。**
偽陽性（振る舞いは正しいのにテストが落ちる）を出すテストは、退行検出力が高くても価値を失う。
開発者がテストを信頼しなくなり、落ちたテストを読まずに直すようになるため。

「退行に対する保護」と「リファクタリングへの耐性」は両立できる。
トレードオフが発生するのは主に「迅速なフィードバック」との間である。

## 2. 依存の分類とモック方針（最重要）

**モックしてよいかどうかは、依存の種類で決まる。** 判断を感覚で行わない。

### 分類の手順

テスト対象が使っている依存を1つずつ取り上げ、次の順に問う。

1. **プロセス内か？** — 同じプロセスで動く自前のクラス・関数か
   → **モックしない。** 実物を使う
2. **プロセス外で、自アプリ以外からも観測できるか？** —
   外部の SaaS、他チームが所有する API、メール送信、課金など、
   呼んだことが自アプリの外に見えるもの
   → **管理外の依存。モックする**
3. **プロセス外だが、自アプリ経由でしか見えないか？** —
   自アプリ専用のデータベース、自アプリ専用のオブジェクトストレージなど
   → **管理下にある依存。原則モックしない**（下記の運用上の例外あり）

判断の決め手は「**そのリソースを他のシステムが直接覗くか**」である。
覗かれるなら、やり取り自体が外部に対する契約なのでモックして検証する価値がある。
覗かれないなら、やり取りは内部実装なので検証対象ではない。

### 運用上の例外

本来、管理下にある依存は実物（エミュレータ）を使って状態を検証すべきだが、
このリポジトリにはエミュレータが未導入のため、**SDK レベルのモックを許容する**。

ただし**許容するのはモックの設置だけで、やり取りの検証は許容しない。**
詳細は次節。この妥協を埋め合わせるのは E2E テストの役割であり、単体テストに背負わせない。

将来エミュレータを導入したら、この例外を削除して実物に切り替える。

## 3. モックとスタブを区別する

テストダブルの検証可否は、それが**コマンド**を模すか**クエリ**を模すかで決まる。

- **モック** = 外部を**操作する**やり取り（コマンド）を模す → **検証してよい**
- **スタブ** = 外部から**データをもらう**やり取り（クエリ）を模す → **検証してはいけない**

**スタブとのやり取りの検証は過剰検証であり、禁止する。**
戻り値を使って最終結果を検証すれば足りるのに、呼び出し方まで固定すると
実装の詳細がテストに焼き付き、リファクタリングへの耐性が失われる。

### 禁止される型

```typescript
// NG: データ取得はクエリ。取得方法の細部は実装の詳細
expect(mockStore.findById).toHaveBeenCalledWith(id, partitionKey);

// NG: クライアントの取得方法は実装の詳細
//     （クライアントをキャッシュする最適化を入れただけで落ちる）
expect(mockClient.getContainer).toHaveBeenCalledWith('images');

// NG: SDK へ渡す引数の形は実装の詳細
expect(mockContainer.getBlob).toHaveBeenCalledWith('abc.jpg');
```

### 推奨される型

```typescript
// OK: 出力値を検証する
const result = await service.getById(id);
expect(result).toEqual({ id, name: '桜' });

// OK: 見つからない場合の振る舞いを検証する
expect(await service.getById('存在しないid')).toBeNull();

// OK: 管理外の依存へのやり取りは検証してよい
//     外部 API の呼び出し回数はコストに直結する観察可能な振る舞い
expect(mockExternalApi.request).toHaveBeenCalledTimes(1);

// OK: 副作用としての削除はコマンド。状態の変化として意味がある
expect(mockStorage.delete).toHaveBeenCalledWith(oldPath);
```

### 例外: 出力が不透明で、外部との契約が引数にしか現れない場合

戻り値が署名済みトークンやハッシュのように**テストから復号できない**値で、
かつその中身が外部システムが検証する契約（権限、有効期限、スコープなど）である場合、
**引数の検証を例外として許容する。**

他に検証手段がないため。権限が read のはずが write になる退行は
セキュリティに影響するので、検出できない状態にしてはいけない。

```typescript
// OK（例外）: 署名済みトークンの中身は検証できないが、
//            権限と有効期限は外部システムが検証する契約
jest.useFakeTimers({ now: new Date('2026-10-11T00:00:00.000Z') });
// …テスト対象を呼ぶ
const [options] = mockedSign.mock.calls[0];
expect(options.permissions).toEqual({ read: true });
expect(options.expiresOn).toEqual(new Date('2026-10-11T00:15:00.000Z'));
```

引数を見るときも、期待値は**完全一致で、リテラルで**書く。
`toMatchObject({ read: true })` は部分一致なので write が加わっても通り、
「現在時刻より後」は有効期限が1年に延びても通る。どちらも防ぎたい退行を見逃す。
時刻は偽のタイマーで固定する（原則6）。

**この例外を使うときは、なぜ他に手段がないかをテスト内のコメントに書く。**
書かないと、後のレビューで原則3 違反として誤って指摘される。

### 判断に迷ったときの問い

> このテストは、**振る舞いを変えないリファクタリング**で落ちるか？

落ちるなら実装の詳細を検証している。検証を結果側に寄せる。

## 4. 観察可能な振る舞いだけをテストする

テスト対象は public API を通じて外から観測できる振る舞いに限る。

- **private メソッドを直接テストしない。** テストしたくなったら、
  それは独立したクラスとして切り出すべき設計上の兆候である
- **private メソッドをテストのために public にしない**
- **型システムを迂回して内部に触らない。**
  TypeScript の `as any` や Dart の動的アクセスでプライベートな状態を
  読み書きするテストは書かない。依存注入が必要ならコンストラクタ引数で受け取る
- **ログ出力の内容を検証しない。** ログは実装の詳細である

HTTP ハンドラにおける「観察可能な振る舞い」は**レスポンスそのもの**
（ステータスコードとボディの内容）である。内部でどのサービスをどう呼んだかではない。

## 5. テストする価値がないコードを見分ける

コードは「複雑度・ドメインの重要性」と「協力者オブジェクトの数」の2軸で分類される。
**両方が低いものは「取るに足らないコード」で、テストを書かない。**

テストを書かないもの:

- 単純な getter / setter
- 1行の委譲だけのメソッド
- 引数を詰め替えてオブジェクトを組み立てて返すだけのコード
- 型定義、定数定義

テストを書くもの:

- 分岐やループを含むロジック
- バリデーションルール。入力空間が広いものは境界値を厚く
  （正規表現1本でも、受理・拒否の境界が多ければテストする価値がある）
- エラーハンドリングの分岐
- 複数の協力者をまとめるオーケストレーション

カバレッジを目的にしない。**取るに足らないコードのテストは、
保守コストだけを増やして退行検出力を上げない負債である。**

逆に、カバレッジが高くても**分岐やエラー経路が未カバーなら退行検出力は低い**。
数値ではなく、どの振る舞いが守られているかで判断する。

### 冗長なテストは削除する

テストは増やすだけでなく**減らす**対象でもある。Kent Beck は
「望む確信を得られる最小限のテストが欲しい」と述べており、
冗長なテストは保守コストと実行時間の負担として扱う。

削除の判断は次の順に行う。

**1. 論理的に従属しているか**

あるテスト A が失敗するとき必ずテスト B も失敗するなら、B は A に従属しており
冗長な候補になる。細かい単位のテストを追加した結果、
上位のテストが同じ条件しか見ていなくなった場合が典型。

**2. 削除すると確信が下がるか（confidence）**

**下がるなら削除しない。** これが最優先の歯止め。
細かいテストを追加しても、**統合的に正しく繋がっていることを保証するテストは1本残す。**
例外処理なら、個別の例外送出のテストを細分化したあとでも
「送出された例外が正しく処理されること」を確認する上位のテストは残す。

**3. 読み手に違うことを語っているか（communication）**

同じコード経路を通っていても、**読み手にとって異なるシナリオを説明している**なら
残す。テストは仕様のドキュメントでもあるため、
実行経路の重複だけを根拠に消さない。

### 削除・再構成を行う手順

**本番コードとテストコードを同時に変更しない。**
両方に欠陥が入ると互いを隠蔽し、テストが通っているのに壊れている状態になる。

1. 本番コードの変更を終え、全テストが緑であることを確認する
2. テストの再構成（重複排除、削除、ヘルパー抽出、改名）を行う
3. **1変更ごとにテストを実行する**

テストの構造は変更してよいが、**期待値の意味は変更しない。**
テストを通すために期待値を書き換えたくなったら、それは振る舞いを変えているサイン。

## 6. テストの構造と命名

### AAA パターン

準備（Arrange）・実行（Act）・検証（Assert）の3段に分ける。

- **実行（Act）は1行であるべき。** 2行以上必要なら、
  public API の設計に問題がある（不変条件を破れる状態を外部に晒している）サイン
- 1つのテストで複数の振る舞いを検証しない
- **テストコード内に条件分岐（if / switch）を書かない。**
  分岐が必要なら2つのテストに分ける

### 命名

`{メソッド名}_{事前条件}_{想定する結果}` のような技術的な命名規則は使わない。
**非開発者が読んでも意味が分かる日本語の文**で書く。

```typescript
// NG
it('getById_notFound_returnsNull', ...)
it('should return null when not found', ...)

// OK
it('存在しないIDを指定した場合はnullを返す', ...)
it('植物でない画像をアップロードすると一時ファイルが削除される', ...)
```

既存テストがこの方針で書かれている場合は踏襲する。

### その他

- **ドメイン知識をテストに漏らさない。**
  期待値をテスト側で計算してはいけない（本番のアルゴリズムを再実装することになる）。
  期待値はリテラルで直接書く
- 現在日時や乱数を直接使わない。固定値を注入するか、
  値そのものではなく形式（ISO 8601 であることなど）を検証する
- **テストごとに状態を独立させる。** グローバルなモック設定や環境変数に
  暗黙に依存するテストは、どの設定が効いているか追えず「保守のしやすさ」を損なう。
  必要な前提はテストファイル内で完結させる

## 7. テストが意図した経路を通っていることを確認する

**緑のテストは、それが検証すると主張しているコードに到達した証拠にはならない。**

到達していないテストは、何も守っていないだけでなく**守られていると誤認させる**。
未検証より有害である。原則2〜6 はテストが対象コードに到達している前提で成り立つので、
この確認はそれらの前提になる。

### 到達できていない典型パターン

**1. 自動モックが本体を隠す**

ライブラリ全体を自動モックすると、モックされた関数が `undefined` を返し、
それを使う本番コードが例外を投げる。本番コードに try/catch の
フォールバックがあると、テストは**フォールバックの出力**を検証してしまう。

本体のロジック（認証、署名、暗号化、整形など）は一度も実行されない。

**2. テスト名と実際の検証対象がずれる**

テストに与えた入力が、検証したい分岐に到達していない。
後続の別の箇所で失敗し、アサーションが緩いために通ってしまう。

**エラーメッセージの前方一致は特に危険。**
`toThrow('〇〇に失敗しました')` は、その接頭辞で包まれた**あらゆる**エラーに一致する。
catch 節が全例外を同じ文言で包む実装では、まったく別の原因で落ちても通る。
検証したい分岐に固有のメッセージか、エラーの型でアサーションする。

**3. テストダブルが引数を無視する**

単一の共有モックオブジェクトが、どの引数で呼ばれても同じ値を返す。
分岐先や宛先を間違える不具合が通ってしまう。
テストダブルは**引数に応じて違う値を返す**よう組む。

**4. ログの抑制が痕跡を消す**

フォールバックが警告を出していても、テスト設定がログを抑制していると気づけない。
ログ抑制は出力を静かにするが、**診断情報も消す**ことを意識する。

### 確認の方法

**変異を入れて、緑のままかを確かめる。** これが最も確実。

- 検証対象のコードを削除する
- 条件を反転させる
- 定数（権限、有効期限、上限値など）を変える

**緑のままなら、そのテストはそこを検証していない。**

補助としてカバレッジで対象の関数・分岐がヒットしているかを確認する。
ただしカバレッジは「通ったこと」しか示さず、
「検証されていること」は示さないため、変異の確認を代替しない。

**変異を入れたらテストスイート全体を実行する。** レビュー対象の1ファイルだけで
緑を確認して「検出されない」と結論しないこと。
単体テストが無力でも、上位のテストが退行を捕まえている場合がある。
そのときの結論は「検出されない」ではなく
**「単体テストが無力で、上位のテストが支えている」**であり、
対処の優先度が変わる（原則5 の「確信が下がるなら削除しない」とも繋がる）。

### 変異を戻す

**変異を入れる前に対象ファイルを退避し、確認後はその退避から戻す。**
バージョン管理の取り消し操作（`git checkout` など）で戻さないこと。
**本番コードが未コミットの状態では、変異ではなく実装そのものを消す。**

戻せたことの確認を「差分が空であること」に置くのも同じ理由で危険。
未コミットの実装がある状態では成り立たない前提になる。
**変異を入れる前の差分と一致すること**を確認する。

変異確認は原則7が最も確実とする手段なので、
**確認のために本番コードを壊して戻す**という性質を常に意識する。
戻し漏れたまま次の作業に進むと、以降のテスト結果がすべて疑わしくなる。

### 書くときの予防

新しくテストを書くときは、**まず落ちることを確認する**。
実装済みのコードに対してテストを書く場合でも、期待値を意図的に誤った値にして
赤になるのを見てから正しい値に直すと、到達していることを確かめられる。
